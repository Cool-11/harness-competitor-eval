# 五款 Harness 竞品评测方案 v1

> 仓库：harness-competitor-eval ｜ 作者：黄钧锶 ｜ 状态：v1 待评审 ｜ 日期：2026-10-10
> 评审对象：Codex / Workbuddy / DSH / 元宝专家模式 / 豆包办公

## 0. 评测立场与红线

**评的是 Harness（执行层脚手架），不是模型排行。**

- 本评测不回答"哪个模型更聪明"，只回答"同一任务交给五款产品，各自的执行层表现出什么差异"
- 红线：不评模型排行；不靠单次跑分下结论；不为分数改标准；每项判断写明置信依据；全部结论可复核（证据可指认、过程可重放）
- 主呈现为**七维度剖面**，不是单一排行榜（总分表仅作辅助索引）

## 1. 评测对象定义

| 产品 | 形态 | 默认配置基线（评测用） |
|---|---|---|
| Codex | CLI 编码 Agent | 官方客户端默认设置，不添加 AGENTS.md 以外的自定义指令 |
| Workbuddy | 桌面 AI 助手 | 出厂默认，不启用任何非默认 Skill |
| DSH | 开源插件化执行层（本地源码运行） | 默认插件集，默认模型路由 |
| 元宝专家模式 | 腾讯元宝桌面端·专家模式 | **专家模式开启**（专家模式本身是被评对象的一部分） |
| 豆包办公 | 豆包办公入口 | 出厂默认，不添加自定义智能体/指令 |

**配置基线规则**：五款一律"出厂默认能力"，不安装任何第三方 SKILL/插件/自定义指令。每款产品的具体版本号、账号状态、配置截图在 `runs/baseline/` 留档。SKILL 变量的处理见 §4.3。

## 2. 评测问题（RQ）

- **RQ1**：五款产品在七个能力维度上（信息回传 / 产物落点 / 失败恢复 / 上下文管理 / 停止条件 / 权限边界 / 可观测性）表现有何差异？
- **RQ2**：观察到的每个失败/差异，应归因于模型、SKILL 还是 Harness？（归因定责框架见 §4）

## 3. 可比性策略（任务层对齐）

五款产品形态差异巨大（CLI / 桌面 / 网页聊天），无法在操作层对齐，因此：

1. **对齐单位 = 任务**：任务书（自然语言指令）五款产品**一字不差**
2. **对齐输入 = 初始文件**：每题统一初始文件包，投喂方式按各产品原生能力（可上传文件的产品上传；CLI 类放工作目录，路径写入任务书）
3. **对齐判分 = 文件产物**：完成条件一律落成文件产物（生成/修改文件），checker 脚本判定 0/1/部分分。文件是最中性的判分落点，五款都能做到
4. **交互差异本身是数据**：过程中产品主动澄清、提问、报告进度的行为，计入"信息回传""可观测性"维度的行为评分，不视为干扰

## 4. 归因定责框架（三层证据链 + 证据分级）

闭源产品（Codex / 元宝 / 豆包 / Workbuddy）**换不了模型**，归因不能只靠换件对照。本方案用三层证据链交叉定责：

### 4.1 三层证据链

- **第一层·探针基线**：每题先做"裸模型探针"——把任务书直接交给裸 LLM（无 Harness、无工具、无文件访问，仅文本），记录其能否完成任务的知识性部分。五款产品共用一组主流模型探针结果做参照基线。→ 建立"模型本身能不能"的参照
- **第二层·DSH 换件对照**：DSH 是本地源码、插件化，可在**其余一切不变、一次只改一处**的前提下换模型 / 拆插件 / 换 SKILL，做真正的控制变量实验。→ 唯一能做实测归因的平台
- **第三层·失败指纹跨产品复现**：对每个观察到的失败，提取"失败指纹"（失败模式的可描述特征：如"读了文件但没写产物""中途放弃未声明""把修改写到了错误路径"），考察同一指纹在其他产品/其他模型上是否复现。→ 指纹可跨模型复现的，倾向 Harness 机制归因；只在单一产品单一模型上出现的，结合第一、二层证据判断

### 4.2 证据等级（每条结论强制标注）

| 等级 | 含义 | 来源 |
|---|---|---|
| **A** | 实测对照 | DSH 换件实验（控制变量）直接证明 |
| **B** | 基线推断 | 探针显示模型本身能做，但 Harness 中失败 → 归责 Harness；或反之 |
| **C** | 指纹复现 | 同一失败指纹跨产品/跨模型复现的行为学证据 |

报告结论表中每一条判断都标注 A/B/C 及依据链接（指向 `runs/` 中的具体现场记录）。

### 4.3 SKILL 变量的隔离

1. 主实验：五款全部默认配置，SKILL 变量被规则冻结（见 §1）
2. 元宝专家模式：专家模式 = 产品的默认形态，是被评对象，**不构成污染**
3. DSH 专项对照：单独跑"带 SKILL vs 裸配置"一组（每配置每题 2 次），SKILL 的边际影响**单独成节**讨论，不混入主对比
4. 主表结论话术统一为"五款产品**默认形态**下的对比"；SKILL 贡献量化只出现在 DSH 专项节

### 4.4 模型变量的边界声明

评测不控制各产品的底层模型（无法控制），因此：
- 所有结论都是"该产品**当前默认模型+默认配置**"下的表现，报告第一章明示此边界
- 探针基线（4.1 第一层）用于判断"失败是否超出模型能力范围"，把模型能力差异从 Harness 归因中剥离
- 产品版本 + 日期在报告结论表逐条标注（Agent 产品迭代快，结论有时效性）

## 5. 用例设计

### 5.1 出题方法论（双轨 + 人工主导）

- **自上而下（维度驱动）**：从七维度反推"这个维度差的产品会怎么失败"，再设计能逼出该失败的任务。方法参考 Harness-Bench（arXiv:2605.27922）的能力维度驱动构造
- **自下而上（真实场景）**：从真实 Agent 使用场景（办公文档、数据整理、多材料综合）改造，任务要有 SWE-bench 式"真实世界气味"，不出玩具题
- **AI 的角色边界**：AI 可辅助打磨措辞、歧义审查、生成初始文件、写 checker 初稿；**题目意图、埋雷点、判定标准必须人工定义**。自检标准：每题"为什么测这个维度"必须能用自己的话讲清楚，讲不清的题废弃

### 5.2 每题四件套

```
cases/T01-xxx/
├── task.md          # 任务书：自然语言指令（五款一字不差）+ 投喂方式说明
├── inputs/          # 统一初始文件包
├── checker.py       # 产物判定脚本（0 / 1 / 部分分，输出判定报告）
└── spec.md          # 完成条件 + 维度映射 + 设计意图（为什么这题能区分）
```

### 5.3 质量关卡（每题过三关才入库）

1. **歧义审查**：让一个 AI 只读任务书，说出两种它认为都合理的解读——两种都合理 = 题目有歧义，改题
2. **难度分层**：预期五款会拉开差距的题保留；预期全对/全错的废题废弃
3. **探针一鱼两吃**：每题顺手跑裸模型探针，其结果同时作为该题的模型能力基线（归因第一层证据）

### 5.4 题量与覆盖矩阵

首批 **14 题**，以覆盖矩阵证明完备性（见 `docs/02-题库骨架-v1.md`）：七维度 × 五类任务类型（文件生成 / 文件修改 / 多步依赖链 / 信息检索汇总 / 埋雷恢复），每维度至少 2 题。第一轮跑完后，**数据驱动**决定是否对区分度不足的维度追加 1-2 题（追加须在评测方案中登记，不得事后无记录加题）。

> 注：团队项目规格书的"30+ 题库"服务于 DSH 换件对照实验（题目×配置矩阵，消耗在 DSH 侧）；本个人作业是 14 题 × 5 产品全量记录。个人 14 题按同款四件套标准出题，即团队题库的种子子集。

## 6. 执行与记录规范（表现现场）

### 6.1 每次运行的记录包

| 记录 | 说明 | 存储 |
|---|---|---|
| 屏幕录像 | GUI 类（Workbuddy/元宝/豆包）全程 | 网盘链接（不进 git） |
| 终端/会话日志 | CLI 类（Codex/DSH）原始输出 | `runs/<case>/<product>/session.log` |
| 产物快照 | 任务结束后整个工作目录打包 | `runs/<case>/<product>/artifacts/` |
| 执行时间线 | 结构化手记 | `runs/<case>/<product>/timeline.md` |

### 6.2 时间线模板（每行一个事件）

```
| 时刻 | 阶段 | 我输入了什么 | 产品做了什么 | 可见输出 | 偏离/异常 | 证据引用 |
```

"证据引用"指向录屏时间戳或日志行号——保证报告里任何一句话都能点回现场。

### 6.3 运行次数

- 常规题：每产品 1 次（结论标注"单次运行"）
- 埋雷题（T05/T06/T07/T14）：每产品 2 次（防运气污染失败恢复数据）
- DSH 换件对照：每配置每题 2 次
- 提效目标：单次记录 ≤40 分钟（时间线模板预建、快照一键归档脚本，W2-3 备好）

## 7. 打分细则框架

### 7.1 两类分数

- **产物分（客观）**：checker 脚本判定，0 / 1 / 部分分，任何人重跑脚本结果一致
- **行为分（量表）**：七维度观察项，每项 0-3 四级（0 未做到 / 1 勉强 / 2 达标 / 3 优秀），**每级写判定锚点**（什么表现给几分），评分依据逐条留痕引用现场记录

### 7.2 可信度机制

- **隔天复评**：行为分在首次评分后隔 ≥24h 复评一次，两次不一致的条目标注并取保守值
- **抽样 kappa**：邀请一位同学对 20% 样本独立复评，计算 Cohen's kappa（≥0.6 为可接受），过程写入"评分可信度"附录——同时回应"结论可复核"要求

## 9. 复核方式（任何人如何验证本评测）

1. 克隆仓库 → 读 `docs/01`（本方案）→ 按 `cases/` 任意一题四件套自行复现
2. `checker.py` 可重跑，产物分一致即可复核
3. 行为分：对照判定锚点 + 现场记录（时间线/录屏/日志）逐条核对
4. 归因结论：按证据等级 A/B/C 定义，沿 §4 框架检查推理链
