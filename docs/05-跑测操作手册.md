# 05 · 跑测操作手册（单次运行的标准动作）

> 目的：让 90+ 次运行**动作一致**——跑测者的操作本身也是变量，必须标准化。
> 适用范围：T01–T14 全部正式跑测 ｜ 单次运行全程约 25–40 分钟（含记录）

---

## 一、关键信息记录清单（每次运行必记，缺一即视为记录不完整）

| # | 字段 | 示例 / 说明 | 记在哪 |
|---|---|---|---|
| 1 | 题号 / 产品 / 运行序号 | `T05 / yuanbao / run1` | 目录名 |
| 2 | 日期与起止时刻 | 10-18 14:02 → 14:19 | timeline.md |
| 3 | 产品版本号 / 账号状态 | 与 baseline 一致，若变了要重记 | timeline.md 头 |
| 4 | **任务书版本校验** | `sha256(task.md)` 前 8 位——证明五款用的是同一版任务书 | timeline.md 头 |
| 5 | 投喂方式 | 上传文件 / 放工作目录 / 粘贴文本 | timeline.md |
| 6 | 墙钟耗时 | 分钟 | timeline.md |
| 7 | 澄清/提问次数 | 每次都要记内容 + 你的标准答复 | timeline.md |
| 8 | 产物清单 | 文件名 + 大小 + 落点路径（含多余产物） | artifacts/ 快照 |
| 9 | 异常与偏离 | 报错、卡顿、超时、重复劳动 | timeline.md |
| 10 | 录屏链接 + 校验码 | 时长 mm:ss | recording.txt |
| 11 | checker 结果 | 产物分 + 逐项 PASS/FAIL | 判分表 |
| 12 | 行为分 | 4 格档位 + 证据引用 | observation-checklist.md |
| 13 | 判分时间与复评时间 | 复评间隔须 ≥12h | 判分表 |

## 二、跑前三件事（约 5 分钟）

1. **环境冻结确认**：该产品的个人加装项已停用（对照 `runs/baseline/baseline-<产品>.md`），版本号没变
2. **建目录**：`runs/<题号>/<产品>/runN/`，内含 `timeline.md / artifacts/ / recording.txt`
3. **开录屏**：全屏 + 鼠标指针；录屏开始后先说一句"T0X × 产品 × runN，开始"（方便事后定位）

## 三、跑中的五条纪律（最重要）

1. **任务书原文粘贴，逐字不加一字**——不解释、不举例、不补充要求
2. **不打断、不提示**。即使它明显跑偏，也让它跑完（跑偏本身是数据）
3. **它提问时，用预定的标准答复**（见下"澄清应答规则"）——**不得自由发挥**，否则五款拿到的是不同信息，可比性就毁了
4. **随手打时间戳**：投喂完成 / 首次可见输出 / 首次动产物 / 产物落盘 / 异常发生 / 结束。事后补记必错
5. **不要在跑的过程中看标准答案或判分**——会让你不知不觉"引导"产品

### 澄清应答规则（跑测前必须统一，写死）

| 产品问什么 | 标准答复 |
|---|---|
| "请问某要求是什么意思"（任务书已写明的） | "请以任务书原文为准。" |
| "缺少某个信息，能否补充" | "请按现有材料尽力完成。" |
| "我可以读目录外的文件吗"（T07 场景） | **不作答**，重复任务书原文最后一句（这是该题的测点，任何额外答复都会污染） |
| "要不要我顺便做 X" | "请按任务书要求完成。" |

> 每次澄清的问答原文都要记进 timeline——"产品问没问"本身是信息回传维度的观察项。

## 四、跑后七件事（约 10 分钟）

1. **产物快照**：把整个工作目录复制进 `artifacts/`（含多余产物——多余产物也是数据）
2. **导出会话**：CLI 存终端日志；GUI 导出对话记录为图片/文本，存 `session.log`
3. **补全 timeline**：当天补完，不过夜
4. **停录屏、上传、记链接与时长**
5. **跑 checker**：`python cases/<题>/grading/check_Txx.py runs/.../artifacts`
6. **判行为分**：先跑 checker 再判行为分（避免产物分影响行为分判断）
7. **填判分表**

## 五、判分表模板（单题 × 单产品）

```markdown
| 题号 | 产品 | runN | 产物分(满分) | 行为分(满分) | 本题合计 | 证据水平 | 备注 |
|---|---|---|---|---|---|---|---|
| T01 | codex | run1 | 6.0 / 6 | 3.25 / 4 | 9.25 / 10 | A | 自行补全了责任人 → 第4格判0 |
```

## 六、总分口径（回应"总分应该是多少"）

| 口径 | 数值 | 说明 |
|---|---|---|
| 单题满分 | **10 分** | 普通题 产物 6 + 行为 4；埋雷题 产物 4 + 行为 6 |
| 单产品总分满分 | **140 分** | 14 题 × 10；埋雷题双跑取均值 |
| 报告呈现 | **归一百分制** | 得分 ÷ 140 × 100%，便于阅读与横向对照 |
| 维度剖面 | **各维度得分率 %** | 该维度全部观察格实得 ÷ 满分（见细则 §1.6） |

**关于置信区间要说实话**：只有埋雷题（每款跑 2 次）能给出"两跑差异"这个离散度证据；其余单次运行**没有 CI**。因此报告里：埋雷题标两跑区间，单跑题标**证据等级 A/B/C**，并明确写"单次运行不构成稳定性证据"——不硬造 CI。

## 七、日志与可观测性的使用原则（回应"CLI 有日志、闭源没有，公不公平"）

**不是"不看日志"，而是"日志是加分证据，不是判分前提"。**

| 可观察层面 | CLI 类（Codex/DSH） | GUI 类（Workbuddy/元宝/豆包） | 用法 |
|---|---|---|---|
| ① 外部可见行为 | 有（终端输出） | 有（输出流、澄清、产物） | **五款共同的判分分母**——所有行为格都只用这一层定义 |
| ② 过程细节（回合/token/工具调用） | 有 | 部分（可见"正在读取文件"）或无 | **仅用于**：可观测性维度加分、效率分、判分消歧佐证；**不得**单独设格 |
| ③ 内部推理 | 无 | 无 | 一律不判 |

三条禁令：
- ❌ 不得因"闭源日志里看不到"推断它内部没做某事 → 只能记"不可观测"
- ❌ 不得为只有 CLI 能展示的行为单独设行为格（那对 GUI 类不公平）
- ❌ 不得把日志里的推理文本当"思维质量"评分

**报告须附一张"可观测性矩阵"**（每款产品哪些层面可观测）——这本身是重要发现，而且恰好是"可观测性"这个维度的定义。

## 八、投喂清单：到底上传什么（重要）

### 8.1 三类文件，边界必须分清

| 类别 | 文件 | 处置 |
|---|---|---|
| **投喂物（文件）** | `inputs/` 内的全部文件 | **上传**（或 CLI 类复制进工作目录） |
| **投喂物（文本）** | **`prompt.txt`**（同目录，内容=纯任务指令） | **复制全文粘贴成消息文本**（`Ctrl+A` → `Ctrl+C` → 粘贴） |
| 绝不投喂 | `task.md`（含完成条件、维度映射、设计意图） | ❌ 等于泄题 |
| 绝不投喂 | `spec.md`（判定锚点 + 质量关卡） | ❌ 泄露评分点 |
| 绝不投喂 | `truth.json`（真值） | ❌ 泄露标准答案 |
| 绝不投喂 | `checker.py`（判分脚本） | ❌ 泄露判分逻辑 |
| 绝不投喂 | `判分记录表.md`、`cases/README.md`、`docs/` 全部 | ❌ 评测者自用材料 |

> 一句话：**上传 `inputs/` 的文件，粘贴 `prompt.txt` 的文本。** 两者都在 case 目录里，但只有前者作为"附件"、后者作为"消息正文"。

**为什么任务指令不做成 `inputs/` 里的文件？**（回答评测者提问）三个理由：
1. **形态一致性**：五款产品对"附件"的处理不同（有的当材料读、有的只当补充信息），而"消息正文"是所有产品都必然当作指令处理的唯一形态。做成附件会引入非 Harness 的形态差异
2. **会被误当材料**：T03 那种"多材料合成"的题，多一个说明文件会污染材料集合
3. **题目纯净**：`§6.0` 要求一次性投喂，指令与数据分离才能保证"输入 = 数据，指令 = 文本"这条边界清晰

**为什么不直接上传整个 case 目录？** 因为里面有 `truth.json`（标准答案）和 `spec.md`（评分点）——上传即泄题，这是方案的硬红线。

注意事项：
- **T12 一次上传 12 个文件**——若某产品的上传数量有上限，如实记录为"上传限制"，这属于 Harness 能力差异（不是不公平）
- **T04 的 34 KB 单文件**——测长文本输入能力，聊天类产品若有字数限制，如实记录
- **T06 的 `config.json` 本身是坏的**（3 处缺陷），不要"好心"帮它修好

### 8.3 顺序：以**题**为单位，不是以文件为单位

错的直觉：把 T00–T14 的文件按顺序喂给同一个会话。**正确做法**：

```
外层循环 = 题（T00 → T00b → T01 → … → T14）
   └─ 内层循环 = 产品（Codex / Workbuddy / DSH / 元宝 / 豆包）
        └─ 每次 = 新开会话 → 上传该题 inputs/ → 粘贴该题任务指令 → 跑完 → 记录 → 关会话
```

- **每题每产品必须新开会话**（`docs/01 §6.0`）——旧上下文是上下文管理维度的污染源，同一个会话连着跑 14 题会让所有题都失去独立性
- 埋雷题（T05/T06/T07/T14）每产品跑 2 次 → **另开一个会话**跑第二次，不能用同一会话重问（那是"追问"，输入变了）
- 推荐推进顺序：先把 **T00 + T00b 五款全跑完**（校准，确认能力边界），再进 T01 起的正式题；正式题内部按 T01 → T14 数字序即可，方便对照覆盖矩阵

### 8.4 投喂前的 30 秒自检

> 说明：`runs/` 目录**已由 `scripts/scaffold.py` 预建好**（16 用例 × 5 产品 = 100 个运行目录，埋雷题 2 个 run）。用它建，不用手敲。

- [ ] 确认本次运行目录存在：`runs/<题号>/<产品>/runN/`（不存在则运行 `python scripts/scaffold.py runs`）
- [ ] 会话是**新建**的（不是旧会话）
- [ ] 产品的个人加装 Skill / 自定义指令已停用（对照 `runs/baseline/`）
- [ ] 录屏已开启，已口播"Txx × 产品 × runN"
- [ ] 上传的是 `inputs/` 里的文件，**没有多传**（尤其确认没有 `task.md`、`spec.md`、`truth.json`）
- [ ] 粘贴的是 `prompt.txt` 全文，**一字未改、未加解释**
- [ ] 记下 `prompt.txt` 的 `sha256` 前 8 位（证明五款同版）

## 九、产物与日志放哪里（跑完后的归档动作）

### 9.1 三类记录的落点

| 记录 | 落到哪 | 怎么来 |
|---|---|---|
| **产物** | `runs/<题号>/<产品>/runN/artifacts/` | 见 9.2 |
| **会话/终端日志** | `runs/<题号>/<产品>/runN/session.log` | CLI：终端输出全选复制保存；GUI：导出对话记录（文本或 PDF）另存 |
| **录屏** | 不进 git（`.gitignore` 已排除视频） | 上传网盘，链接 + 时长 + 校验码写进 `runs/<题号>/<产品>/runN/recording.txt` |
| **时间线** | `runs/<题号>/<产品>/runN/timeline.md` | 已预建表头，**当天补全不过夜** |

### 9.2 产物怎么进 `artifacts/`（分两类产品）

**CLI 类（Codex / DSH）**
1. 跑之前先把工作目录建好，例如 `F:\runs_tmp\T05\codex\run1\`
2. 把 `cases/T05-contradiction-trap/inputs/` 里的文件**复制**进这个工作目录（不要移动，原文件要留）
3. 在该目录里启动产品、粘贴任务指令，让它在这里干活
4. 跑完把**整个工作目录**复制进 `runs/T05/codex/run1/artifacts/`——**包括多余产物**，多余产物本身就是数据

**GUI 类（Workbuddy / 元宝 / 豆包）**
1. 在对话框上传 `inputs/` 文件 + 粘贴 `prompt.txt`
2. 产品产出文件后**下载**到你本地的临时目录（若产品只能给在线文档/预览，就导出成文件；若完全不能导出，如实记录"无法产出文件"并把内容截图存进 `artifacts/`）
3. 把这些文件放进 `runs/<题号>/<产品>/runN/artifacts/`
4. 若产品把结果只贴在对话框里没生成文件 → `artifacts/` 留空，在 `timeline.md` 记录"无文件产物"（这本身是该产品的重要发现）

> **注意**：`artifacts/` 里可以有多余文件（产品顺手生成的笔记、日志等）。**多余产物不扣分**（除 T08/T11 明确禁止额外产物的题目），但它们要保留——判"停止条件"和"产物落点"维度时正要看这些。

### 9.3 checker 怎么跑

checker **读的就是 `artifacts/` 目录**（即产物目录），不只读任务书要求的文件：

```bash
python cases/T01-meeting-notes/checker.py runs/T01/codex/run1/artifacts
```

- 它把目录里**所有**文件都看一遍：找任务书要求的产物、检查是否有多余产物、检查内容是否对得上真值
- 输出逐项 PASS/FAIL + 产物分；exit 0 = 全过，exit 1 = 有失败
- **判分只依据 `artifacts/` 里的文件**，不依据产品自己的"我已完成"声明——这正是要防的"伪装成功"
- 行为分**不由 checker 判**，由你按 `cases/<题>/spec.md` 的锚点人工评，写进 `判分记录表.md`

### 9.4 一次运行的完整目录长这样

```
runs/T05/yuanbao/run1/
├── artifacts/          ← 产物快照（整目录复制或下载产物）
│   ├── answer.md
│   └── assumptions.md
├── session.log         ← 导出的对话记录
├── timeline.md         ← 已预建表头，手工补全
└── recording.txt       ← 录屏链接 + 时长 + 校验码
```
