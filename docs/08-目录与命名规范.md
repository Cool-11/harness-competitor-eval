# 08 · 目录与命名规范

> 触发：2026-10-16 整理前，仓库出现三层投喂副本（`tasks/<题>` / `inputs/` / `inputs-txt/` / `tasks/first_tasks/all-inputs/`）互相打架，其中 `tasks/first_tasks/all-inputs/` 混入 2 个旧版本文件，取件时可能拿错导致实测作废。
> 结论：**真源唯一、取件处只读、现场不改写、留档可回滚。** 本规范固化整理后的口径，后续新增内容一律照此执行。

---

## 一、四层职责（谁是真源，一句话讲清）

| 层 | 目录 | 职责 | 能否直接编辑 |
|---|---|---|---|
| **真源** | `tasks/<批次>/<题号>/` | 唯一权威内容：`task.md` · `prompt.txt` · `inputs/` · `checker.py` · `spec.md` · `truth.json` | ✅ 只能改这里 |
| **取件** | `tasks/first_tasks/all-inputs/` · `tasks/second_tasks/all-inputs/` | 投喂文件的取件副本（S 批按题目子目录，避免同名覆盖） | ❌ 只读，从真源同步 |
| **现场** | `Log-analyse/` | 实测记录：时间线 · 日志 · 产物 · 录屏链接 | ⚠️ 只追加，不改历史 |
| **留档** | `_archive/` | 整理前快照 + 路径迁移记录 | ❌ 只读，不入 git |

**判断口诀**：要改内容 → 改 `tasks/<批次>/<题号>/`；要拿文件投喂 → 从对应批次取件区取；要记结果 → 写 `Log-analyse/`。

## 二、目录命名规范

### 2.1 题库

```
tasks/<批次>/<题号>-<英文slug>/
  例：tasks/first_tasks/T00-hello-world/ · tasks/first_tasks/T14-silent-anomaly-trap/
      tasks/second_tasks/S06-artifact-deep-path/
```

- **批次层（2026-10-21 新增）**：`tasks/first_tasks/`（T00–T14）· `tasks/second_tasks/`（S01–S35）；旧路径 `cases/` 已整体改名为 `tasks/`
- 题号：**基线层** = `T` + 两位数字（校准题用 `T00` / `T00b`）；**压力层** = `S` + 两位数字（`S01`–`S35`）。均**两位定宽**便于排序
- slug：全小写英文 + 连字符，概括考点（`contradiction-trap` 而非 `trap2`）
- 模板目录固定为 `tasks/_template/`，下划线前缀表示"非正式题"

### 2.2 现场

```
Log-analyse/<题号>/<产品>/run<n>/
  例：Log-analyse/T05/yuanbao/run2/
```

- **产品名固定五个 slug，不得简写**：`codex` · `dsh` · `workbuddy` · `yuanbao` · `doubao`
  - ❌ 禁止 `wb` / `yunbao` / `元宝` / `Workbuddy` 等变体（2026-10-16 已统一）
- `run<n>` 从 `1` 起，不留前导零
- 每个 run 目录固定四件套：`timeline.md` · `session.log` · `artifacts/` · `shots/`，另加 `recording.txt`
- 埋雷/静默题每产品两个 run（基线层 `T05/T06/T07/T14`；压力层**以各题 `task.md` 声明为准，共 12 题**：`S11/S12/S13/S14/S15/S24/S26/S27/S28/S29/S31/S33`），其余一个
  - ⚠️ 历史口径不一致（docs/09 曾列 11 题、本文件曾列 8 题）——2026-10-21 起统一按 `task.md`，其余文档待同步

### 2.3 非标准现场

确有不能套用 `<题号>/<产品>/run<n>` 的批次（如跨题日志分析），集中放在 `Log-analyse/` 下**单一名目录**，并在 `Log-analyse/README.md` 登记说明：

```
Log-analyse/<产品>-log-analyse/             ← 五款批量日志现场（2026-10-21 由 Five-app-log-analyse 改名）
  └─ artifacts/first-run-artifact|second-run-artifact/<题号>/ + shots/<题号>/ + recording/
Log-analyse/S-batch/<题号>/<产品>/run<n>/               ← 压力层现场；结果表 Log-analyse/S-batch/results.md（由 scripts/sbatch.py collect 写入）
```

### 2.4 其他固定目录

`docs/` · `scripts/`（含 `sbatch.py` 跑批脚手架）· `Log-analyse/baseline/`（基线 + 回滚包）· `Log-analyse/S-batch/`（压力层现场 + 结果表）· `Log-analyse/`（批量日志现场）· `_archive/`（留档）· `tasks/_template/` · `tasks/first_tasks/all-inputs/` · `tasks/second_tasks/all-inputs/`（两批取件区）

## 三、文件命名规范

| 类型 | 规范 | 示例 |
|---|---|---|
| 题库四件套 | **固定小写名，不得改动** | `task.md` · `prompt.txt` · `checker.py` · `spec.md` |
| 机读真值 | 固定名 | `truth.json` |
| 判分表 | 固定名 | `判分记录表.md` |
| 现场记录 | 固定名 | `timeline.md` · `session.log` · `recording.txt`（2026-10-23 起：`recording.txt` = **产品外部日志**，不再记录录屏链接） |
| 投喂指令副本 | `<题号>-<slug>_prompt.txt` | `T01-meeting-notes_prompt.txt` |
| 文档 | `<两位编号>-<名称>-v<版本>.md` | `01-评测方案-v1.md` · `08-目录与命名规范.md` |
| 周报 | `周报<两位序号>-<MMDD>-<状态>.md` | `周报01-1017-草稿.md` |

### 3.1 投喂附件为什么是中英混用（不是错误，别改）

`tasks/<批次>/<题号>/inputs/` 里的附件名（`合同-A.md`、`会议纪要-1.md`、`background.md`…）**被任务书逐字引用**：

```
prompt.txt：请阅读附件 `会议纪要-1.md` …
```

改名必须同步改 `task.md` + `prompt.txt` + `spec.md` + `checker.py` 里的引用，且已跑过的 `Log-analyse/` 记录会全部失配。**因此附件名按"创建即冻结"处理，不做规范化重命名。**

## 四、投喂纪律（唯一口径）

1. **会话策略（2026-10-21 拍板）**：采用 **方案 A——一个产品一个会话连续跑完一组（每组 5 题，按维度分组，见 `tasks/second_tasks/BATCH-PLAN.md`）**。由此产生的上下文延续属于**可比较性缺陷**，判分时须在「上下文管理」「产物落点」维度标注"不可比"，并在报告局限一节如实说明
2. **附件**：只挂本题 `inputs/` 里的数据文件（1~30 个），文件从对应批次的取件区取（T 批 `tasks/first_tasks/all-inputs/`；S 批 `tasks/second_tasks/all-inputs/`）
3. **指令**：把该题 `prompt.txt` 的正文**复制粘贴**到对话框，作为消息文字
4. **绝不投喂**：`task.md` · `spec.md` · `truth.json` · `checker.py`（泄题 / 泄真值）
5. **绝不整体投喂**取件区：T 批 47 个文件、S 批 33 个题目录混投会让题目失去指向、破坏题间隔离
6. **投喂前记哈希**：`sha256(prompt.txt)` 与 `sha256(inputs/*)`，与 `timeline.md` 表头核对

## 五、文档格式规范

所有 `docs/*.md` 统一结构：

```markdown
# <编号> · <标题>

> 触发：<为什么写这份>
> 结论：<一句话给出判断>

---

## 一、<节>
## 二、<节>
```

- 标题用 `# 编号 · 标题`（全角间隔号）
- 用 `>` 引用块写"触发 / 结论"，让读者 5 秒抓住要点
- 用 `---` 分隔元信息与正文
- 表格优先于长段落；锚点/判据一律**编号**（`§5.2`、证据⑧）便于交叉引用

## 六、变更纪律

| 变更类型 | 正确动作 |
|---|---|
| 改题目内容 | 改 `tasks/<批次>/<题号>/` 真源 → 同步对应取件区 → 记 `sha256` |
| 改已跑完的现场 | **不改**。新增 `timeline.md` 补注或另起 run |
| 改历史日志/判分输出 | **绝不改**（属原始证据）；如路径失效，写进 `_archive/README.md` 的路径迁移记录 |
| 移动仓库位置 | 移动后更新 `_archive/README.md` 的路径迁移表，并在 `Log-analyse/README.md` 提示旧绝对路径 |
| 整层目录结构变动 | 先把原目录复制进 `_archive/<日期>-整理前快照/`，校验一致后再动 |

## 七、整理后的自检清单

每次新增或整理后跑一遍：

```powershell
# 1. 取件区与真源是否一致（T 批 prompt；S 批 inputs）
Get-ChildItem tasks\first_tasks -Directory | Where-Object { $_.Name -match '^T\d' } | ForEach-Object {
  $short = ($_.Name -split '-')[0]
  $a = (Get-FileHash (Join-Path $_.FullName 'prompt.txt')).Hash
  $b = (Get-FileHash (Join-Path 'tasks\first_tasks\all-inputs' "${short}_prompt.txt")).Hash
  if ($a -ne $b) { "不一致: $short" }
}
Get-ChildItem tasks\second_tasks -Directory | Where-Object { $_.Name -match '^S\d\d-' } | ForEach-Object {
  $src = Join-Path $_.FullName 'inputs'; $dst = Join-Path 'tasks\second_tasks\all-inputs' $_.Name
  if (Test-Path $src) {
    Get-ChildItem $src -Recurse -File | ForEach-Object {
      $rel = $_.FullName.Substring($src.Length)
      if (-not (Test-Path (Join-Path $dst $rel))) { "缺件: $($_.Name)$rel" }
    }
  }
}

# 2. 产品目录口径是否统一（应只有五个）
Get-ChildItem Log-analyse -Directory | ForEach-Object { $_.Name -replace '-log-analyse$','' } | Sort-Object -Unique

# 3. T 批现场目录是否齐备（每题 × 五产品）
Get-ChildItem tasks\first_tasks -Directory | Where-Object { $_.Name -match '^T\d' } | ForEach-Object {
  $id = ($_.Name -split '-')[0]
  foreach ($p in 'codex','dsh','workbuddy','yuanbao','doubao') {
    if (-not (Test-Path "Log-analyse\$id\$p")) { "缺: Log-analyse\$id\$p" }
  }
}
```

## 八、任务卡与运行证据规范（2026-10-22 新增）

> 触发：对照 WildClawBench `tasks/` 结构后确认——本项目"任务卡缺机读字段、checker 缺分项输出、run 目录缺效率证据"。
> 结论：**任务卡加 YAML 头、checker 加可选机器可读块、run 目录固定三件套**；只做加法，不改题面、不改 `docs/03` 冻结口径。

### 8.1 任务卡 YAML 头

**新增**题目在 `task.md` 顶部必须有 frontmatter；存量 T00–T14 / S01–S35 **只回填头，不改正文**。

```yaml
---
id: S06-artifact-deep-path
batch: second            # first | second
dimension: D2            # D1–D7（docs/09 §1.1）
part: P5                 # P1–P9（docs/09 §1.2）
failure_code: A2-B1      # docs/10 §1.3 两轴编码
stress: 深路径+中文名+指定编码
breaking_point: 路径≥3层且含中文/空格时开始落错
failure_signature: 落到根目录而非指定目录
timeout_seconds: 600
modality: pure-text
repeat: 1                # 埋雷题=2，与 §2.2 口径一致
---
```

- `id` 必须与目录名逐字一致；`dimension` / `part` / `failure_code` 只能取受控词表，不得自由发挥
- frontmatter 只服务机读与聚合，**不是投喂内容**（投喂仍只用 `prompt.txt`）

### 8.2 checker 分项输出（可选，不动打分口径）

- 人类可读输出保持现状（`合计：x/y` 仍是产物分的唯一来源）
- checker 可选择在**最后一行**输出 `METRICS_JSON: {"分项名": 0.0~1.0, ...}`；分项名用小写英文 + 下划线
- 没有该行时，`score.json.metrics` 记空对象，不视为失败
- **本规范只定义输出格式，不新增评分档**——0–3 锚点与权重仍以 `docs/03`（v1 冻结）为准

### 8.3 运行证据三件套

每个 `Log-analyse/.../run<n>/` 固定新增三个 JSON（由 `scripts/sbatch.py collect` 生成，人工只补效率字段）：

| 文件 | 字段 |
|---|---|
| `manifest.json` | `case` `product` `run` `started_at` `ended_at` `prompt_sha8` `inputs_sha8` `artifacts_count` `checker_exit` `interventions` `rerun` |
| `usage.json` | `elapsed_seconds` `turns` `timed_out` `manual_interventions` |
| `score.json` | `raw_got` `raw_full` `metrics` `failure_code` `evidence_grade` `status` |

**2026-10-30 v2 强制项**：新运行另须在 `prepare.json` / `manifest.json` / `run.json` 保存不可复用 `run_id`、单题 `task_revision`、产品版本、模型、工具、权限、Skills/Memory 状态、接口预检和最终终裁。禁止覆盖已有 `run<n>` 槽位；重跑另起 run。正式比较准入规则与六类分账见 `docs/22`。

**v2 试点追加（2026-10-22）**：S06 试点在以上三件套之外，另加 `prepare.json`（开始时间/哈希）、`run.json`（终止原因/绑定/评分/首错/证据）、`grade.yaml`（人工 Rubric 分 + 证据引用）、`badcase.yaml`（失败才建）；完整结构与返回清单见 `docs/15-S06试点运行卡-v0.1.md`。

口径：

- `elapsed_seconds` **只做描述统计，不进总分、不跨产品比秒数**（模型思考强度不可控）；`timed_out=true` 是二值失败事件，必须计入
- `failure_code`（`docs/10` 两轴）与 `evidence_grade`（A/B/C）由人工判分后回填，脚本先留空
- `score.json.status` 取 `graded` / `not_applicable` / `timeout`

### 8.4 "形态不支持"

产品形态无法完成任务（无可安装技能包、无文件系统、无联网等）时：

- 记 `status: not_applicable`，**不进分母、不判 0**
- 在结果表**单列一行**，报告里说明原因
- 与 `docs/02` T04"输入框限制如实记录"同口径：这是 Harness 形态差异，不是能力 0 分

### 8.5 真值封存三步

桌面端无容器隔离，用流程替代：

1. 投喂前对工作目录做"可见文件清单"截图，存 `shots/`
2. `checker.py` / `truth.json` / `spec.md` 不进入投喂路径
3. 判分时才解封，并在 `timeline.md` 记录**解封时间**
