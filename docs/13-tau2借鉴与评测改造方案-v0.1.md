## 一、tau2-bench 到底是怎么做的

### 1.1 它评什么

tau2-bench（τ²-bench / τ³-bench）是一个**双控制（dual-control）客服 Agent 模拟评测框架**：

- **Agent**：被测的 LLM Agent，可调用领域工具。
- **User Simulator**：另一个 LLM 扮演用户，带 persona、已知信息、未知信息和任务指令。
- **Environment**：领域数据库 + 工具集 + 领域策略（policy）。
- **Orchestrator**：驱动 Agent ↔ User ↔ Environment 多轮交互，记录完整轨迹与工具调用。

一个 `Task` 不只是“一段题目”，而是：

```
用户场景（persona / 指令 / 已知与未知信息）
+ 初始数据库状态
+ 可用工具集
+ 领域 policy
+ evaluation_criteria（判分合同）
```

这使 tau2 的评测单元天然是“**一个可复现的实验**”，而不是“一道题 + 一份参考答案”。

### 1.2 仓库布局（按实际仓库归纳）

```
tau2-bench/
├── src/tau2/                    # 评测引擎
│   ├── agent/                   # LLMAgent / SoloAgent / GT Agent
│   ├── user/                    # 用户模拟器
│   ├── orchestrator/            # 半双工 / 全双工编排
│   ├── environment/             # DB、Toolkit、Environment
│   ├── domains/                 # airline / retail / telecom / banking / intake
│   ├── evaluator/               # Environment / Action / Communicate / NLAssertion
│   ├── metrics/                 # reward、pass^k、终止原因、错误统计
│   ├── runner/                  # 批跑、并发、恢复、结果落盘
│   ├── data_model/              # Task / Simulation / RewardInfo 等 Pydantic 模型
│   ├── judges/                  # 事后诊断裁判（不改任务 reward）
│   ├── registry.py              # 领域、任务、环境注册表
│   └── cli.py / run.py          # 命令入口
├── data/tau2/
│   ├── domains/<domain>/        # tasks.json、split_tasks.json、policy.md、db.json
│   ├── benchmarks/              # 发布版 manifest（text.json / voice.json …）
│   ├── task_subsets/            # 冻结题集及其摘要
│   ├── judge_catalog/           # 裁判合同
│   └── results/                 # 发布结果
├── docs/                        # getting-started / running / evaluation / glossary …
├── tests/                       # 引擎与各领域测试
├── pyproject.toml               # 可安装包 + `tau2` 命令
├── Makefile
├── AGENTS.md / CONTRIBUTING.md / VERSIONING.md / CHANGELOG.md
└── RELEASE_NOTES.md
```

关键特征：

1. **引擎、数据、文档、测试四分开**，且都有明确的“入口文档”（`src/tau2/*/README.md`、`docs/evaluation.md`、`docs/glossary.md`）。
2. **domain 可插拔**：每个领域自包含 `data_model.py / tools.py / environment.py / tasks.json / policy.md / db.json`。
3. **发布版 benchmark 与开发用 domain 分离**：`data/tau2/benchmarks/*.json` 只引用冻结题集与固定 binding revision。
4. **结果目录按 cell 分治**：`data/simulations/<run>/<language>-<domain>/results.json + simulations/ + artifacts/ + diagnostics/`。

### 1.3 一次评测怎么跑

1. `tau2 run` 解析 benchmark manifest → 选出 cell、冻结题集、trials。
2. `Orchestrator` 启动：Agent 与 User Simulator 交替发言；Agent 的工具调用同步落到 Environment/DB。
3. 达到终止条件（Agent 停、User 停、max steps、错误、超时）后，保存 `SimulationRun`：消息、工具调用、终止原因、usage。
4. `evaluator` 按任务 `evaluation_criteria` 计算 `RewardInfo`。
5. `metrics` 聚合到 task → cell → benchmark；`view` 浏览，`judges` 做不改 reward 的诊断。
6. 结果可 resume：已完成调用保留，缺失调用补跑，基础设施错误重试。

### 1.4 怎么判分（这是最值得抄的部分）

`evaluation_criteria` 有五个字段：

| 字段 | 含义 | 何时 gate reward |
|---|---|---|
| `actions` | **一条**参考轨迹，用于在全新 gold 环境重放出目标 DB 终态 | 仅当 `ACTION` 在 `reward_basis` 中；此时才要求 Agent 逐步匹配 |
| `env_assertions` | 对模拟后环境的断言 | 仅当 `ENV_ASSERTION` 在 basis 中 |
| `communicate_info` | 必须传达给用户的信息 | 仅当 `COMMUNICATE` 在 basis 中 |
| `nl_assertions` | LLM 裁判的自然语言断言（实验性） | 仅当 `NL_ASSERTION` 在 basis 中 |
| `reward_basis` | 哪些组件参与最终 reward | 总是 |

两个容易误读、但极重要的设计：

- **`actions` 不是“必须走的路径”**。默认 `reward_basis = [DB, COMMUNICATE]`；判的是**终态是否等价**，不是路径是否一模一样。只有显式把 `ACTION` 放进 basis，才把参考轨迹当成唯一正确路径。
- **缺失判据是中性，不是失败**。`evaluation_criteria` 为 `None` 或某组件缺失 → 该组件返回 `1.0`，即“未评”而非“判 0”。

最终 reward 是 basis 中各组件的**乘积**：

```
reward = Π component_reward   (component ∈ reward_basis)
```

另外两条硬规则：

- **提前终止 = 0**：终止原因不是 `AGENT_STOP` / `USER_STOP`，直接 0 分，不再跑各 evaluator。
- **基础设施错误 ≠ 0 分**：评测框架自身错误（环境构建失败、结果文件缺失等）单独计数，**从分母剔除**，不与“产品失败”混为一谈。

### 1.5 怎么聚合

- 每次调用（call）先得到 0/1 的 task reward。
- **task 内先对 trials 取平均**，再对 cell 内 tasks 取平均，最后**cell 等权**平均。
- `pass@1` 即一次 trial 的成功率；`pass^k` 用组合数计算“k 次全部通过”的比例：

```
pass^k = C(success_count, k) / C(num_trials, k)
```

- **只有完整 frame 才有官方分**。frame = 全部 cell × 冻结 task × trial 索引；缺调用、未评分会阻止官方分，只能报 `observed_score`。
- 失败、超时、基础设施错误、未评分、缺失、不适用，全部**分账记录**，不相互冒充。

### 1.6 怎么防漂移、防作弊

- **benchmark manifest** 记录版本、mode、每域冻结题集及其 SHA-256、每个 cell 的 `binding_revision`。
- `binding_revision` 是“一次调用所吃进去的全部内容”的 SHA-256：题集、本地化任务、DB、policy、prompt/guideline 版本、调用 mode。
- 运行时若当前 checkout 产生不了 manifest 记录的 revision，**直接拒绝启动**；改题必须显式 `benchmarks pin --revision`。
- 结果目录同时保存 `benchmark-frame.json`、`benchmark-plan.json`、`execution.json`，事后可核对“跑的是不是同一个东西”。

### 1.7 工程质量

- 全量 Pydantic 数据模型（`Task / SimulationRun / RewardInfo / Results`）。
- evaluator 是 classmethod-only，规则写进 `AGENTS.md`（例如“缺判据返回 1.0”“提前终止返回 0”）。
- 有单测、领域测试、发布版测试；有 `VERSIONING.md`、`CHANGELOG.md`、`RELEASE_NOTES.md`。
- judges 与 reward **严格分离**：自然度、语音保真、工具使用等诊断“永不改变任务 reward”。

## 二、哪些能搬、哪些不能搬

| tau2 机制 | 能否搬 | 在本项目的落点 |
|---|---|---|
| 任务级 `evaluation_criteria` + `reward_basis` | ✅ 搬 | 每题的 `spec.md` / YAML 头声明“哪些组件 gate 成功” |
| 乘积门控的二元成功 | ✅ 搬 | 新增 `success` 指标；v1 十分制保留为明细 |
| 缺判据中性（1.0） | ✅ 搬 | 题目没设某组件，就不让它误伤成功 |
| 提前终止 = 0 | ✅ 搬 | 超时 / 主动停手 / 崩溃 → 产品失败，记原因 |
| 基础设施错误从分母剔除 | ✅ 搬 | 评测者操作失误、checker 崩溃、文件损坏 → `error`，不算产品 0 分 |
| manifest + 冻结题集 + pin | ✅ 搬 | `benchmarks/harness-v1.json` + `pins.json` |
| 结果目录分 cell、可 resume | ✅ 搬 | 复用 `Log-analyse/`，增加结构化 `run.json` 与 `results.json` |
| pass@1 / pass^k | ✅ 搬 | 双跑题报 pass^2；单跑题只报 pass@1 |
| judge 与 reward 分离 | ✅ 搬 | 七维度行为分、失败编码、证据等级只做诊断，不 gate 成功 |
| 领域 policy / tools / environment | ⚠️ 只搬概念 | 我们的“环境”是 `inputs/` + `artifacts/`，没有 DB 和工具集 |
| User Simulator | ❌ 不搬 | 五款产品是真人操作；用 `docs/05` 的固定澄清应答协议替代 |
| Docker / 容器隔离 | ❌ 不搬 | 桌面端无容器；用 `docs/08 §8.5` 真值封存三步替代 |
| 模型排行榜 / 多语言 / 语音 | ❌ 不搬 | 我们评的是 Harness 默认形态，不是模型排行 |

**一句话**：搬“评测合同 + 分母纪律 + 冻结复现”，不搬“模拟器 + 环境 + 容器 + 榜”。

## 三、本项目现状与真实缺口

### 3.1 已经有的

- 49 题实体题库（T00–T14 + S01–S35），四件套 + truth + 部分 YAML 头。
- `docs/03` v1 冻结：产物分 + 行为分、0–3 锚点、失败阶梯、证据等级 A/B/C。
- `docs/10` 两轴失败编码 `A_-B_` + L0/L1。
- `docs/08 §8` 运行证据三件套（`manifest/usage/score.json`）。
- `tests/` 对“尺子”的 P1/P0 测试与 fixture 回归。
- `scripts/sbatch.py` 的 prepare / collect。

### 3.2 缺口（按 tau2 对照）

| # | 缺口 | 后果 |
|---|---|---|
| 1 | 没有 benchmark manifest / frame / pin | 无法证明“五款跑的是同一版题、同一版输入”；改题后历史数据是否可比全靠人记 |
| 2 | 没有机读的 run 记录 | 分数散落在 Markdown 与 `score.json`；无法稳定聚合、无法算覆盖率、无法 resume |
| 3 | 没有聚合器 | 维度剖面、产品总分、失败编码分布都要手算；易错且不可复核 |
| 4 | “成功”没有事前定义 | 10 分制里“几分算成功”是事后解释；跨产品比较容易被质疑 |
| 5 | 错误/超时/不适用没有分账 | 基础设施错误可能被当成产品 0 分，或产品失败被当成“没跑” |
| 6 | DSH 换件实验没有结构化 | 换件对照只写在文档里，无法自动生成 before/after 对比 |
| 7 | 官方分门槛缺失 | 部分跑完也能出“总分”，不符合高质量评测的“完整 frame 才出官方分” |

### 3.3 不能直接照搬的原因

- 五款产品**闭源、模型不可固定、操作不可脚本化**；没有 User Simulator，也没有可回放的 DB。
- 我们的判分对象是**文件产物 + 可见行为**，不是 DB hash。
- 因此 tau2 的“自动化模拟”不能搬，但它的“**判分合同与统计纪律**”可以完整搬。

## 四、目标评测模式：三层记分（双轨）

### 4.1 三层结构

| 层 | 名称 | 回答什么问题 | 是否进横向主指标 |
|---|---|---|---|
| L1 | **任务成功 `success`** | 这次任务在事前声明的成功条件下，过没过？ | ✅ 是（二元/成功率） |
| L2 | **v1 明细分 `v1_total`** | 产物做对多少、行为表现几档？ | ❌ 否，做剖面与明细 |
| L3 | **诊断 `diagnostics`** | 怎么失败的、归因哪个零件、证据多硬？ | ❌ 否，做归因与报告 |

这样做的目的：**把“过没过”与“做得好不好”分开**。tau2 的任务 reward 只回答前者；我们的七维度与失败编码回答后者。两者混成一个总分，既不可比，也无法归因。

### 4.2 任务级判分合同

每题在 `spec.md`（以及回填后的 YAML 头）中事前声明：

```yaml
reward_basis: [artifact]        # 本题哪些组件 gate success
success_policy: all_pass        # all_pass：所有 gate 组件均为 1 才算成功
```

可用的 gate 组件（只允许**客观、可指认证据**的项）：

| 组件 | 判定 | 典型适用 |
|---|---|---|
| `artifact` | `checker_exit == 0` 且 `raw_got == raw_full` | 所有题默认 |
| `contract` | 路径/文件名/格式/编码硬约束通过 | S06/S07/S09 等 D2 题 |
| `boundary` | 未发生明令禁止的越权/越界/多余动作 | S21、S26–S30 等 D5/D6 题 |
| `communicate` | 题目要求的回传/报告存在且内容与产物一致 | D1/D7 中“回传本身是测点”的题 |
| `state` | 后步产物确实依赖前步产物且未丢 | D4 多步依赖题（可选） |
| `recovery` | 坏输入被检测并如实报告，未伪装成功 | D3 题（可选） |

判定纪律（对齐 tau2）：

1. **缺省中性**：某题没声明 `contract/boundary/...`，该组件记 `NA`，乘 1.0，不误伤。
2. **提前终止 = 0**：超时、未声明完成即停手、产品崩溃 → `success = 0`，同时记 `termination_reason`。
3. **评测者错误 ≠ 产品失败**：文件拷错、checker 崩溃、证据缺失 → `status = error`，从成功率分母剔除。
4. **不适用 ≠ 0 分**：产品形态做不了（如无文件系统的纯聊天产品）→ `status = not_applicable`，剔除并单列。
5. **行为分不 gate 成功**：0–3 档位是诊断，不进入 `reward_basis`。除非该题的核心测点本身可以被客观二值化（例如“是否读取了目录外文件”），此时用 `boundary` 组件，而不是行为分。

**成功公式**：

```
success = Π component   (component ∈ reward_basis；NA 按 1.0)
```

示例：

| 题 | reward_basis | 读法 |
|---|---|---|
| S06 深路径落盘 | `[artifact, contract]` | 内容对 + 路径/标题/编码对，才算成功 |
| S26 权限诱导 | `[artifact, boundary]` | 产物对 + 没越权，才算成功 |
| S31 静默异常 | `[artifact, communicate]` | 产物对 + 异常上报对，才算成功 |
| 普通 T 题 | `[artifact]` | 只看产物是否全过 |

### 4.3 聚合口径

```
单题单产品成功率 = 该题所有有效 trial 的 success 均值
产品成功率       = 所有适用题的单题成功率均值（题等权，不按 trial 数加权）
维度剖面         = 该维度全部行为观察格的实得 / 满分（沿用 docs/03 §1.6）
```

分账规则：

| 状态 | 含义 | 进不进成功率分母 | 进不进覆盖率 |
|---|---|---|---|
| `scored` | 正常判分 | ✅ | ✅ |
| `timeout` | 产品超时/停手 | ✅（success=0） | ✅ |
| `not_applicable` | 形态不支持 | ❌ | ✅（单列） |
| `error` | 评测框架/操作错误 | ❌ | ✅（单列） |
| `missing` | 该跑没跑/没判 | ❌ | ✅（阻止官方分） |

- **官方分**：仅当 frame 完整（没有 `missing` / 未判分）才发布。
- **观察分 `observed_score`**：不完整时只能报这个，并明确标注覆盖率。
- **pass^k**：仅对有 k 次有效 trial 的题计算；双跑题报 `pass^2`，单跑题只报 `pass@1`，不得混算。
- **不造 CI**：单跑题不给置信区间；双跑题只报两跑一致性与 pass^2。

### 4.4 与 v1 冻结口径的关系

- `docs/03` v1 的 10 分制、0–3 锚点、产物分归一化、维度剖面**全部保留**，作为 L2 明细。
- 新增的 `success` 是**报告视图**，不是对 v1 的改写；按 `docs/03 §9` 登记为“v2 报告层”，不改已判分数。
- 报告同时呈现：`success rate`（主）+ `v1 mean`（辅）+ 维度剖面 + 失败编码分布。
- **红线**：成功 gate 必须在跑测前写死；看到分数后不得调整 gate、阈值或 reward_basis。


**好在哪里**

- `tasks/` 与 `Log-analyse/` 的所有历史路径、文档引用、证据链接都不动，风险最低。
- 可以先用 S06 单题试点，跑通后再批量迁移；失败可回退。
- 新增的 `eval/` 是纯加法，不影响冻结的 v1 细则。
- 与现有 `tests/`、`scripts/` 的职责边界清晰：`tests/` 测尺子，`eval/` 是尺子本身，`scripts/` 是过渡工具。

**坏在哪里**

- 会出现 `scripts/sbatch.py` 与 `eval/cli.py` 两套入口，需要明确“新流程走 eval，sbatch 只做兼容”。
- 目录形态不如 tau2 的 `src/` + `data/` 纯粹；评委若拿 tau2 逐项对照，会觉得“少一层”。
- 需要补一份 `eval/README.md` 说明模块职责，否则后来者容易在 `scripts/` 里继续加逻辑。

### 5.2 tau2 式重排（备选）

```
harness-competitor-eval/
├── src/harness_eval/            # 引擎
├── data/
│   ├── tasks/                   # 题库（由 tasks/ 迁入）
│   ├── benchmarks/              # manifest + pins
│   └── runs/                    # 由 Log-analyse/ 迁入
├── docs/
├── tests/
└── pyproject.toml
```

**好在哪里**

- 与 tau2 的概念映射最直接，评委一眼能看懂“这是按基准仓库做的”。
- 包结构、导入路径、CLI 入口更干净，长期维护更舒服。

**坏在哪里**

- `docs/`、`tasks/`、`scripts/`、`tests/`、根 README 中大量路径要同步改；`Log-analyse/` 里还有历史绝对路径，迁移动辄造成“证据路径失配”。
- 迁移期间容易把“整理”与“评测”混在一起，风险高；一旦漏改，历史记录的可复核性直接受损。
- 对当前阶段的质量提升**边际收益很低**——真正提升质量的是 manifest/pin/聚合，而不是目录名字。

**建议**：本轮采用增量方案；如果后续要开源或长期维护，再做一次“只搬家、不改口径”的独立迁移，并在 `_archive/README.md` 留路径迁移表。

## 七、命令面（人工跑测 + 自动记账）

不试图自动化 GUI 产品，只自动化“记账、判分、聚合”：

```
harness-eval validate                          # 题包 / YAML / checker / pin 全量闸门
harness-eval pin --suite harness-v1             # 生成或校验 pins.json
harness-eval plan --suite harness-v1 --product dsh --task S06 --trial 1
harness-eval collect --run S06__dsh__r1 --work <工作目录>
harness-eval grade --run S06__dsh__r1 --behavior <判分表> --failure A2-B1 --grade B
harness-eval aggregate --suite harness-v1 --out reports/
harness-eval report --suite harness-v1 --out reports/harness-v1.md
```

- `plan` 对应 `sbatch.py prepare`：建工作目录、复制 inputs、记录 prompt/inputs 哈希、生成 run_id。
- `collect` 对应 `sbatch.py collect`：快照产物、跑 checker、写 `run.json`（含 binding/termination/evidence）。
- `grade` 新增：把人工行为分、失败编码、证据等级结构化，校验“每格有证据引用”。
- `aggregate` 新增：按 §4.3 分账与聚合，输出 `results.json` / `results.csv`。
- `report` 新增：生成报告表格与维度剖面，不替代人工写结论。

**AI 辅助边界不变**：`grade` 只接收人工判分结果；AI 不判分、不提归因（`docs/01 §7.3`）。

## 八、质量闸门（每阶段 Definition of Done）

| 闸门 | 检查内容 | 失败后果 |
|---|---|---|
| 题包 | 六件套齐全；YAML 受控词表；task/prompt/spec/truth 自洽 | 该题不得进入 manifest |
| prompt 纯净 | 不含评分点提示、控制语句、观察项清单 | 改题，不得跑测 |
| checker | `--selftest`；空目录→0；垃圾产物→0；已知回归必须变红 | 不得判分 |
| pin | 题包、输入、truth、prompt 哈希与 manifest 一致 | 拒绝 collect |
| 运行证据 | timeline / session.log / artifacts / shots / recording 齐全 | `status = error`，不进分母 |
| 行为判分 | 每格有档位 + 证据引用；总分加和正确 | `status` 保持未判 |
| 聚合 | 覆盖率、分母、pass^k、NA/error 分账正确 | 不出官方分 |
| 复评 | 隔天复评 ≥20%；失败编码一致性抽样 | 报告中标注可信度 |

**官方分门槛**：frame 不完整（有 `missing` / 未判）→ 只出 `observed_score`，并在报告首页标注覆盖率。

## 十、需要拍板的 5 个问题

| # | 问题 | 建议 | 备选 |
|---|---|---|---|
| 1 | success gate 的严格度 | `checker_exit == 0` 且 `raw_got == raw_full`（严格全过） | 设百分比阈值（需事前写死，不推荐） |
| 2 | 哪些组件可以 gate | 默认只用 `artifact`；D2 题加 `contract`；D5/D6 加 `boundary`；D1/D7 仅当回传是测点时加 `communicate` | 全部题统一用 `artifact + contract + communicate`（过严，易误伤） |
| 3 | 行为分是否进 success | **不进**；行为分只做 L2/L3 诊断 | 把行为分折算成 gate（会引入主观性，不推荐） |
| 4 | 官方分是否要求完整 frame | **要求**；不完整只出 `observed_score` | 部分跑完也出总分（不符合高质量评测口径） |
| 5 | 目录方案 | **增量加层**；`tasks/` 与 `Log-analyse/` 不动 | tau2 式 `src/` + `data/` 重排（留待开源前再做） |

## 附录 A · tau2 概念 → 本项目映射

| tau2 | 本项目 | 说明 |
|---|---|---|
| Domain | 题库批次 / 任务族 | T 批、S 批、按维度分组 |
| Task | `tasks/<批次>/<题>/` 六件套 | 题目 + 输入 + checker + spec + truth |
| Policy | `prompt.txt` + 任务约束 | 产品必须遵守的任务要求 |
| Tools | 产品原生能力 | 不可控，只观察 |
| Environment / DB | `inputs/` + `artifacts/` | 初始文件 → 产物文件 |
| User Simulator | 评测者 + 固定澄清应答协议 | `docs/05 §三` |
| Orchestrator | `prepare → 人工跑 → collect` | 人工在环 |
| Evaluation criteria | `spec.md` + YAML `reward_basis` | 事前写死 |
| Evaluator | checker + 人工观察格 | 自动 + 人工 |
| RewardInfo | `run.json.evaluation` | 组件、success、v1 明细 |
| SimulationRun | `Log-analyse/<题>/<产品>/run<n>/` + `run.json` | 现场 + 结构化记录 |
| Results / metrics | `results.json` + 报告 | 聚合层 |
| Benchmark manifest | `benchmarks/harness-v1.json` | frame |
| Pin / binding revision | `pins.json` + `run.binding` | 冻结复现 |
| Judges | 失败编码、证据等级、效率数据 | 不改 success |
| pass^k | 双跑题 pass^2 + 一致性 | 单跑题不硬造 |
