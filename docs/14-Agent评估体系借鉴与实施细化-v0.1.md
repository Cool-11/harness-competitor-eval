## 一、第 7 章的评估体系骨架（按原文黑体标题归纳）

### 1.1 评估对象：模型 + Harness，而不是模型

- 同一模型在不同 Harness 中差异巨大；评估应评“模型与 Harness 的组合体”。
- 区分“模型能力不足”与“Harness 设计缺陷”的常见手段是 **model swap**：固定 Harness 只换模型；换强模型不涨 → 瓶颈在 Harness；换弱模型大跌 → 瓶颈主要在模型。
- 另有 **ablation**：逐一关闭 Harness 组件，看整体性能变化。
- 对本项目：五款闭源产品不能换模型；DSH 可换件/换模型，是唯一能拿到 A 级因果的平台。其余四款只能用条件对照 + 失败指纹，结论等级最高到 B/C。这个边界必须在报告里写死。

### 1.2 评估体系四环节

原文把评估拆成四个环节：

1. **什么算成功**（指标与口径）
2. **任务从何而来**（数据集来源）
3. **由谁验证**（验证器与可信度）
4. **分数如何转化为决策**（统计、归因、回归、选型）

这四环节正好对应本项目当前的四块短板：成功合同、任务来源登记、验证者可信度、分数到决策。

### 1.3 一条任务的解剖：τ²-bench telecom

一条任务包含四部分：

| 部分 | 作用 | 本项目对应 |
|---|---|---|
| `ticket` | 给 Agent 的工单/任务描述 | `prompt.txt` |
| `user_scenario` | 给用户模拟器的 persona、已知/未知信息、任务指令 | 评测者 + 固定澄清应答协议；`inputs/` 中的信息不对称 |
| `initial_state` | 初始状态重置脚本 | `inputs/` 快照 + 工作目录哈希 |
| `evaluation_criteria` | 过程/结果验证标准 | `spec.md` + `checker.py` + 行为观察格 |

四个设计要点：

1. **显式建模用户认知边界**：`known_info` 只给用户已知的三项，故障根因不在其中；Agent 必须通过提问和引导获取。这是“渐进式信息透露”，不是靠提示词约束模拟器。
2. **防止用户模拟器被 Agent 忽悠**：情绪设定、验收口径（只有测速 excellent 才算解决）、事实锚定（用户回答必须以工具返回为依据）。缺少事实锚定，模拟用户会顺着 Agent 确认“已解决”，评估退化为两个模型互相确认。
3. **双方都不具备完全信息**：故障在用户侧，Agent 查数据库只能得到“配置正常”；必须引导用户操作。双控让“Agent 是否真的读到用户侧操作结果”也成为验证维度。
4. **多维过程 + 结果校验**：`env_assertions` 验终态，`actions` 验关键动作，`communicate_info` / `nl_assertions` 验必要信息是否告知。每个任务可选其中一个或多个维度，用 `reward_basis` 聚合。

对本项目的直接启发：

- 我们的题目虽然没有 User Simulator，但可以**显式写清“产品不知道什么、必须自己从材料里发现什么、评测者知道但绝不补充什么”**。这就是 `information_asymmetry` 字段。
- 我们的固定澄清应答协议就是“用户模拟器”的替代品；必须写死“不确认对错、不补充信息、不帮产品做判断”，否则会污染测点。
- 我们的 checker 只验产物，七维度观察格验过程；两者不能互相替代。尤其要单独统计“产物对但回传错”的比例。

### 1.4 评估指标：Pass@k、Best@k、Pass^k

- **Pass@k**：同一任务跑 k 次，至少一次通过；连续分数取最好一次为 **Best@k**。衡量“能力上限/技术奇观”。
- **Pass^k**（Pass consecutive k）：同一任务连续 k 次都通过，且不能触发安全/合规/幻觉等一票否决。衡量“业务可靠性”。
- 关系（独立同分布假设）：`Pass@k = 1-(1-p)^k`，`Pass^k = p^k`。
- 报告必须写清 k 的口径：是同一任务的 k 次独立采样，还是生产流水线上连续 k 个任务；有副作用的操作不能“重试到成功”，要在沙盒/可回滚环境采样，并记录每次失败。

对本项目：

- 单跑题只能报 `Pass@1`；双跑题可报 `Pass^2`，但 k=2 噪声很大，只能作描述性指标，不能据此排名。
- 不应把 `Pass@2` 与单跑题的 `Pass@1` 混在一张表里比较。
- 报告要写“独立采样、每题新会话”的口径。

### 1.5 评估环境的五个组成要素

| 要素 | τ²-bench | 本项目 |
|---|---|---|
| Dataset | 任务文件：初始状态、工单、模拟器规范、验收标准 | `tasks/<批次>/<题>/` 六件套 |
| Environment State | 数据库 + 设备侧开关，可重置 | `inputs/` + 工作目录；每 run 重新复制、记哈希 |
| Tools | Agent 侧 + 用户侧原子工具 | 产品原生能力；不可控，只记录“能力矩阵” |
| Rubric | `evaluation_criteria` 四层检查 + `reward_basis` | `checker.py` + `spec.md` 行为锚点 + 成功合同 |
| Interaction Protocol | 用户 `###STOP###`、轮数上限、耐心耗尽 | 一次性投喂、固定澄清答复、产品宣告完成/超时/轮数上限 |

五要素缺一，评估就不是可重复循环。本项目最缺的是 **Environment State 的重置语义**与 **Interaction Protocol 的终止条件枚举**；这两项应在任务卡中显式声明。

两类环境：

- **人机交互型**：验证沟通策略与引导能力（τ²-bench）。
- **工具调用型**：验证可观测状态变更（SWE-bench、Terminal-Bench、AndroidWorld）。
- 本项目是“人机交互 + 文件产物”的混合体：产品形态不同，但判分落点统一为产物；过程行为用七维度观察。

### 1.6 评估数据集的设计

#### 验证器深度

- SWE-bench Verified：`FAIL_TO_PASS` + `PASS_TO_PASS` 双重验证，前者证明“修好了”，后者证明“没弄坏”；还要排除 flaky test。
- OSWorld：134 个独立评估函数，检查文件系统、进程、网络、应用内部状态；不仅看报告文件是否存在，还连接数据库核实 SQL 是否真的执行。
- Terminal-Bench：真实执行，Agent 无法伪造输出。
- GAIA：精确字符串匹配；答案必须组合多源信息，且部分任务配专有附件。

对本项目：

- 每题 checker 应拆成 **必需变更（required）** 与 **不得破坏的不变量（invariant）** 两类。当前多数 checker 只验“产物有没有/对不对”，缺“旧文件有没有被覆盖/其他行有没有被误删/格式有没有被破坏”的不变量。
- 对“表面完成、实质错误”要专门设反例：文件存在但内容为空、CSV 行数列数对但值错、报告声称完成但产物缺失。
- 对 flaky 要有检查：同一 fixture 多次跑 checker，结果必须稳定；checker 自身进入回归测试。

#### 难度划分

- GAIA 三级：L1 单/双工具；L2 多步；L3 复杂组合。每级失败指向不同改进方向。
- Terminal-Bench 从简单模型注册到困难多组件集成。
- τ²-bench 专设陷阱任务：用户声称“客服已批准”，实际不符合政策，测 Agent 能否维持正确判断。

对本项目：

- 把 T 批标为 L1（基础执行），S deep 标为 L3（击穿/组合），S light 标为 L2（中等压力）。
- 维度诊断要写清：L1 失败 → 基础工具/文件能力；L2 失败 → 多步执行/上下文；L3 失败 → 长链、恢复、边界、终止。
- 难度标签要跑测前写死，不能根据分数事后调整。

#### 数据泄漏防范

- GAIA：多源组合 + 专有附件，单网页无法直接给答案。
- AndroidWorld：参数化模板实例化，每次随机参数，固定操作序列失效。
- Terminal-Bench：题面嵌入 canary GUID，输出含 GUID 即说明数据进入训练集。

对本项目：

- 题库公开后，静态题容易被产品厂商纳入评测调优集。至少做三件事：
  1. **参数化变体**：对深跑题生成 2–3 个同考点、不同参数（姓名、数字、路径、文件数）的实例；主表用固定实例，变体用于鲁棒性抽测。
  2. **canary 标识**：在 prompt/inputs 中埋唯一标识，检查产物/会话是否复现；复现即标记“疑似泄漏/记忆”。
  3. **私有 holdout**：留一部分题不公开题面与真值，只公开统计口径。
- 不应把“防泄漏”理解为一次性动作；它是持续监控。

#### 质量控制与长期维护

- τ²-bench 从 τ-bench 迭代了五处：任务指令太笼统 → 拆 known/unknown；成功条件不精确 → excellent 才算解决；模拟用户太机械 → 加情绪/耐心/事实锚定；用户也参与操作 → 双控；实例动态生成。
- SWE-bench Verified 从 2294 题中人工筛到 500 题，淘汰约 71%。
- OSWorld 发布后 15 个月暴露 300+ 问题：环境、描述歧义、验证过严/过松、初始状态不完整。

对本项目：

- 建立 **题目健康表**：每题的修订次数、oracle 修复、歧义修复、checker 回归、最后一次验证日期。
- 建立 **题目淘汰率**：出题—自检—试跑—淘汰的比例；不要只记录“建成了多少题”。
- 建立 **问题登记**：像 T02 oracle 错这种，必须进入 `KNOWN_ISSUES`，修复后回归。

#### 评估集的三个来源

1. 公开基准：粗筛与借鉴设计，不直接用于产品决策。
2. 自建业务集：覆盖真实任务分布，用于模型/Harness 决策。
3. 生产轨迹回流：真实失败案例，经归因后沉淀为回归用例，成本最高、准确性最高。

对本项目：

- 已有自建业务集；缺“生产轨迹回流”的正式通道。
- 可以把 `Log-analyse/` 中的真实 BadCase 转为 `badcases/` 与 `regression/`，形成“越跑越强”的评估资产。

### 1.7 自动化评估方法

原文的验证谱系：从确定性验证器 → 检查项清单 → Rubric → LLM-as-a-Judge → 配对比较。原则是 **能写成断言的一律用断言；LLM 只用于确实无法机械判定的维度**。

#### Rubric 四准则（Scale AI, Rubrics as Rewards）

1. **基于专家指导**：反映领域知识，捕捉核心事实与推理步骤。
2. **全面覆盖**：事实准确性、逻辑连贯性、完整性、安全性；不仅写正面标准，还要写 **Pitfall（陷阱）**。
3. **按重要性加权**：必要项（Essential）、重要项、可选项、陷阱项；支持 **Veto（一票否决）**。
4. **评价标准自包含**：每项独立可操作，不依赖评价者的领域知识；避免“展示了深刻理解”，改为“引用了至少两个权威理论并准确解释如何支持结论”。

关键实践：

- 每档给可验证的具体行为，不只给抽象形容词。
- 提供示例与边界案例。
- 防奖励作弊：明确惩罚幻觉、讨好用户、关键词堆砌、回避棘手问题。
- Rubric 要迭代：收集分歧，逐步从抽象准则变成判例集。

#### LLM-as-a-Judge 的偏差

- 长度偏差：倾向给更长、更详尽的回答高分。
- 位置偏差：配对比较时偏向先出现的候选。
- 同源模型问题：Agent 与 judge 同家族，Agent 可能学会利用 judge 的偏好和盲点（Goodhart）。
- 缓解：Rubric 显式惩罚冗长/设长度上限；配对时控制长度；交换顺序各评一次；多源异构 judge（不同模型家族）；相同 Rubric；加权平均或一致性检查；部署期单模型快评 + 定期完整审计。

#### 多模态 judge

TTS、ASR、UI、视频剪辑等；本项目可借鉴“截图/界面状态”的多模态诊断，但官方分仍应由 checker + 人工决定。

### 1.8 失败归因：从整条轨迹定位首个错误

- 端到端评估只给“成功/失败”，不回答“为什么、从哪一步开始”。
- 归因对象是 **首个导致任务偏离的错误**；后续错误往往是连锁反应，不能把最后一个报错当根因。
- 结构化记录：主要错误类别、首错步骤、工具调用/模型输出、可复核证据、根因 vs 后果、是否可恢复、置信度。
- 规则先筛、LLM 再定位：完成声明与实际命令交叉核对、diff 是否触及测试断言/skip、diff 是否改公开 API/schema 而无迁移。
- 错误分类示例：需求理解与歧义、流程与规范缺失、工具调用错误、hack 验证环境、修改不完整、对用户的信息反馈错误、非功能性回归、模型执行异常、过早停止任务。

三个典型案例：

1. **“做对了但说错了”**：τ²-bench 704 次有信息告知要求的运行中失败 240 次，其中 162 次是信息告知出错；80 次（占全部失败 1/3）环境状态正确但告知错误。只验环境状态会完全漏掉这一类。
2. **AndroidWorld T3A**：Agent 32 步无工具报错，自行宣告完成，但验收失败。首错在第 8 步的 assistant message（“I cannot actually see the content/details of the expenses in the image”），它已知没拿到数据却继续推进，第 11 步开始编造四条开销。根因不是“模型不会 OCR”，而是 T3A 是纯文本 Agent，观察空间只有元素树、没有图像像素——**Harness 观察通道缺失**。若记成模型能力问题，改进方向会完全错。
3. **精确复制错误**：`old_string` mismatch 不能只归因“模型抄错”；要沿“文件原始字节 → 工具返回 → Harness 序列化 → 模型上下文 → token 输出 → 解码 → JSON/tool-call 解析 → 工具匹配”逐层找首个差异。

对本项目：

- 七维度回答“哪类行为弱”，A/B 轴回答“怎么结束、在哪失配”，但都还没回答“**哪一步开始错**”。必须新增 `first_error_step`。
- 要区分 `root_cause_layer`：model / harness-observation / harness-tool / harness-memory / harness-termination / task-oracle / evaluator。
- “做对了但说错了”要单独设指标：`artifact_pass & communicate_fail`。这正是 D1/D7 的价值，不能被总分或二元成功掩盖。
- 对 GUI 产品，“看不到图片/附件内容”可能是 Harness 观察通道缺失，不是模型不会 OCR。要在能力矩阵里记录。

### 1.9 端到端回归与轨迹前缀回归

- **端到端回归**：从初始状态和请求开始，跑完整任务，检查最终状态、输出、安全条件。接近生产结果，但难判断失败在哪一步。
- **轨迹前缀回归**：冻结首错之前的上下文、对话、工具返回、环境状态，只要求 Agent 思考并执行下一步或下几步可观察动作。成本低，能隔离单个策略/工具问题。
- 答案应是 **可接受动作集合**，不是唯一动作；同时列禁止动作。
- 对高可靠生产 Agent，轨迹前缀回归往往比端到端回归更重要。

对本项目：

- 这是最值得新增的资产类型。可以从 `Log-analyse/` 的 BadCase 中截取首错前的前缀，构造 `regression/prefix/` 任务：
  - 输入：前缀上下文摘要 + 当前工作目录快照。
  - 要求：只输出下一步动作（如“先读某个文件”“先询问”“拒绝越权”）。
  - 判定：动作 ∈ 可接受集合；不触发禁止动作；证据引用完整。
- 对闭源产品，前缀任务可以作为“诊断探针”：在新会话中重建上下文，观察它下一步怎么做。结论等级标 C（行为学证据），不混入主成功率。
- 对 DSH，可以做真正的控制变量：同一前缀，换件前后对比。

### 1.10 评估结果的统计显著性

- 有限评估集 + 随机性 → 分数差异可能只是噪声。
- 标准误：`SE(p) ≈ sqrt(p(1-p)/n)`；95% CI 约 `p ± 1.96·SE`（小样本用 Wilson）。
- 同一批任务比较两个配置，优先 **配对分析**：逐题记录谁胜出，用 McNemar 或 paired bootstrap，而不是直接相减两个独立成功率。
- 每个配置最好多个随机种子（3–5 次），报告均值与波动；单次运行只能筛方向。
- 多重比较：收紧显著性阈值，或对正向结果独立复跑。
- 判断标准：分差要超过噪声、在配对分析中成立、可复现，才值得据此切换/发布。

对本项目：

- 五款产品 × 49 题天然是配对设计；应按题配对比较，而不是只比总分。
- 49 题、成功率 70% 时，95% CI 约 ±13 个百分点；小于 10 个百分点的差异很可能只是噪声。报告必须写 n 与 CI。
- 五款两两比较有 10 组，需做多重比较校正或只预注册少数主比较。
- 双跑题只能报一致性与 `Pass^2`，不能硬造 CI。

### 1.11 可观测性与内部评估

- Trace/span：一次任务一条 trace，每次 LLM 调用、工具调用、检索是一个 span，记录输入输出、起止时间、token、错误。
- 标准协议：OpenTelemetry / OpenInference；采集与分析解耦。
- 平台：LangSmith / Langfuse / Arize Phoenix；A/B、prompt 版本管理、协作。
- 生产轨迹回流：筛选失败/可疑案例 → 脱敏 → 沉淀为评估集与回归测试。

内部评估基础设施：

- 消融：每个主要特性可独立关闭，定期验证真实贡献。
- AB 测试：多臂而非二元；区分机制指标与目标指标；设护栏指标；记录基线统计。
- 双层特性开关：编译时物理移除 + 运行时下发。
- 提示词敏感性：系统提示可确定性渲染、版本化快照、每次变更跑回归。
- 隐私感知分析：类型系统强制约束，而不是文档规范。

对本项目：

- 已有 timeline / session.log / shots / recording，接近 trace，但字段不统一。应升级为 `run.json` 的结构化事件流。
- 闭源产品看不到内部 span，只能记“不可观测”；不得推断内部没做某事。
- DSH 是唯一可做消融/换件的平台；应把换件实验做成正式 `variant`，记录完整 config 哈希与护栏指标。

### 1.12 从 Benchmark 报告到系统改进

- 看到表现下降，**先检查评测系统本身**：资源不足、验证器 bug、用例与生产脱节，都可能伪装成模型退化。
- 读报告先找失败簇，不盯总分；再回放轨迹，分清“看、想、做、验”。
- 假设驱动、单变量实验：H1 提示词 → H5 观察通道 → H5C 精简元素树。
- 小样本结果只能支持下一步，不外推整体；完整复测通过才能谈部署。
- 报告要写清：结论适用范围、哪些底线没通过、下一轮验证什么。

对本项目：

- 报告模板要从“结论汇编”升级为“决策备忘录”：每条结论带 n/CI/证据等级；明确未证明项；给出下一轮实验。
- 失败簇按 D1–D7 / P1–P9 / 首错步骤聚合；不要只给五款总分。
- 先查 oracle/checker/证据，再谈产品归因（T02 教训）。

## 三、目标评估体系 v2（草案）

### 3.1 四环节落地

#### 环节 1：什么算成功

三层指标，回答不同问题：

| 指标 | 公式/口径 | 回答的问题 | 用途 |
|---|---|---|---|
| `Pass@1` | 单次任务成功率的均值 | 一次交付大概多可靠 | 主报告 |
| `Pass^k` | k 次全过比例（组合数） | 连续 k 次都不出错有多难 | 双跑题/关键任务 |
| `v1_total` | 产物分 + 行为分（0–10） | 做对了多少、过程多好 | 明细与维度剖面 |
| `state_ok_communicate_fail` | 产物过 ∧ 回传/告知失败 | 是否“做对了但说错了” | 专项诊断 |
| `veto_triggered` | 幻觉/越权/改测试/伪造完成 | 是否触发一票否决 | 直接判定失败 |

成功合同：

```yaml
reward_basis: [artifact, contract]   # 只有客观组件能 gate
success_policy: all_pass
veto: [fabrication, unauthorized_access, fake_completion]
```

规则：

- `artifact`：checker 全过（`exit 0` 且 `raw_got == raw_full`）。
- `contract`：路径/文件名/格式/编码硬约束。
- `boundary`：未发生越权/越界/禁止动作。
- `communicate`：要求告知的信息已告知，且与产物一致。
- `veto`：触发即 0，不论其他组件。
- 未声明的组件记 `NA`，乘 1.0。
- 提前终止/超时 → 0，并记终止原因。
- 评测框架错误 → `status=error`，剔除分母。

#### 环节 2：任务从何而来

三条来源，登记在 `benchmarks/harness-v1.json`：

1. **自建业务集**：T/S 题库（主体现）。
2. **公开基准机制借鉴**：SWE-bench 双验证、τ² 四层检查、Terminal-Bench 真实执行、GAIA 多源答案。
3. **生产轨迹回流**：`Log-analyse/` BadCase → `badcases/` → `regression/`。

任务卡新增字段（只加头，不改题面）：

```yaml
difficulty: L2                 # L1/L2/L3
information_asymmetry:         # 产品不知道、必须自己发现的信息
  agent_unknown: [...]
  evaluator_only: [...]
success_contract:
  reward_basis: [artifact]
  success_policy: all_pass
  veto: [fabrication, unauthorized_access]
interaction_protocol:
  max_turns: 20
  termination: [product_declared_done, timeout, evaluator_stop]
environment_reset:
  inputs_sha256: "..."
  visible_files: [...]
leakage_guard:
  canary: "HC-EVAL-..."
  variant_seed: null
regression_of: null            # 若由 BadCase 转化，填 badcase_id
```

#### 环节 3：由谁验证

验证者分层：

| 层 | 验证者 | 适用 | 可信度来源 |
|---|---|---|---|
| 1 | checker / 确定性脚本 | 文件存在、内容、格式、必需变更、不变量 | 负控制 + 回归 + flaky 检查 |
| 2 | 人工 Rubric | 过程行为、沟通、报告质量 | 双评 + κ + 证据引用 |
| 3 | LLM judge（仅审计/预筛） | 大规模初筛、分歧发现 | 金标集 + κ + 偏差审计 + 人工仲裁 |
| 4 | 多源异构 judge | 高风险/抽样复核 | 不同模型家族 + 一致性 |
| 5 | 人工终判 | 官方分 | 最终权威 |

原则：

- **能机械判定的不交给 LLM**。
- LLM judge 不直接进入官方分；它先证明自己“在什么范围内、以多高一致性”可信，才可用于预筛或辅助。
- 人工终判保留，尤其是 veto、边界、归因。

#### 环节 4：分数如何转化为决策

决策规则（跑测前写死）：

1. **先查评测系统**：oracle、checker、证据完整性、运行环境。确认不是评测系统问题，再谈产品。
2. **看失败簇**：按 D1–D7 / P1–P9 / 首错步骤 / 任务类型聚合，不盯总分。
3. **配对比较**：同题五款配对；McNemar（二元）或 paired bootstrap（分数）；报告 n、效应量、CI。
4. **多重比较校正**：10 组两两比较 → Bonferroni/FDR，或只预注册 2–3 组主比较。
5. **护栏指标**：成功率提升不能以 token/时延/越权/幻觉恶化为代价。
6. **小样本不外推**：12 题深跑只能支持“下一步验证”，不能写成 49 题整体结论。
7. **决策类型**：保留 / 修 Harness / 换模型 / 加题复测 / 证据不足。每种都要写触发条件。

### 3.2 Rubric v2：从“打分表”升级为“测量仪器”

#### 四准则落地

| 准则 | 本项目做法 |
|---|---|
| 基于专家指导 | 每个维度锚点由评测者按真实任务定义；引用 `docs/01` 的 Harness 视角；不写“回答得好”这类外行标准 |
| 全面覆盖 | 产物正确性 + 过程行为 + 沟通 + 安全/边界 + 效率；每个维度写 Pitfall |
| 按重要性加权 | 必要项（gate 成功）、重要项（计分）、可选项（加分）、陷阱项（veto） |
| 自包含 | 每档写“看到什么给几分”，附示例与边界案例；不依赖评价者领域知识 |

#### 权重与 veto

```yaml
rubric:
  dimensions:
    - name: 产物正确性
      weight: essential          # 必要项，未过即失败
      levels: {...}
    - name: 信息回传
      weight: important          # 重要项，计分
      levels: {...}
    - name: 可观测性
      weight: optional           # 可选项，加分
      levels: {...}
    - name: 安全边界
      weight: veto               # 一票否决
      levels:
        pass: "未读取/写入任务目录外文件，未执行禁止动作"
        fail: "发生越权/越界/伪造完成/编造数据"
```

注意：

- `essential` 与 `veto` 的区别：essential 是“必须做对”，veto 是“绝对不能做错”。
- 行为分仍不 gate 成功；`essential` 只用于客观组件（artifact/contract/boundary）。
- 主观维度（回传质量、可观测性）只做 `important/optional`，不做 gate。
- 权重与 veto 必须跑测前冻结；看到分数后不得调整。

#### 自包含锚点示例（D2 产物落点）

| 档 | 判定（可指认） | 示例 | 边界案例 |
|---|---|---|---|
| 3 | 路径/文件名/编码/标题全对，且主动确认落点 | 产物在 `输出/汇总/月报_v1.md`，UTF-8-SIG，标题 `# 月报` | 产物对但没主动确认 → 2 |
| 2 | 路径/文件名/编码/标题全对，但未主动确认 | 同上，无确认语句 | 路径对但标题多一个空格 → 1 |
| 1 | 路径对但标题/编码错，或需追问才改 | 落到 `输出/汇总/月报.md` | 路径对、标题错、编码对 → 1 |
| 0 | 未产出/落错路径/只在聊天框 | 产物在根目录或对话里 | 落错但自己发现并改对 → 2 |

#### 防奖励作弊（Pitfall）

- 幻觉：编造输入中不存在的数据/来源。
- 伪造完成：声称完成但产物缺失/为空。
- 改测试/改真值：修改 checker、truth、断言以通过。
- 关键词堆砌：用评分关键词凑内容，但事实错误。
- 过度输出：用大量无关内容掩盖缺失。
- 讨好用户：顺着用户错误前提编答案。
- 回避：对关键歧义不声明、不处理。

这些应进入 Rubric 的 veto/pitfall 项，并有负控制 fixture。

### 3.3 LLM-as-a-Judge 可信度协议

**先回答“能不能保证一定对”：不能。** LLM judge 是一个测量仪器，不是 oracle。我们能做的是：在明确的适用范围、Rubric 版本和任务分布内，证明它 **足够可信、偏差可控、可复现**。

#### 十步验证协议

1. **限定使用范围**：只用于无法机械判定的主观维度；能用 checker 的不用 judge。
2. **建立金标集**：分层抽样（易/中/难、通过/失败、各维度、边界案例），由人工独立标注；金标集与正式评估集分离，避免过拟合。
3. **冻结 judge 配置**：模型版本、prompt、Rubric 版本、temperature、seed、最大 token；每次判决随结果保存。
4. **一致性指标**：
   - 二分类：Cohen's κ；多分类/多评者：Krippendorff's α；连续分：ICC。
   - 每个维度单独算 precision/recall/F1 与混淆矩阵，不只看总体准确率。
   - 报告 95% CI 与样本量。
5. **重测稳定性**：同一输入重复 N 次（温度 0），看判决一致率与分数方差。
6. **多源异构**：至少两个不同模型家族 + 人工仲裁；一致才计入，不一致送人工。
7. **偏差审计**：
   - 长度偏差：分数与回答长度的相关性；
   - 位置偏差：A/B 交换顺序各评一次；
   - 风格/品牌/情绪偏差：中性化改写后复评；
   - 关键词偏差：删除关键词但保留语义，看分数是否异常下降。
8. **扰动不变性**：同义改写、段落重排、加无关内容、换格式；judge 判决应基本不变。
9. **校准与阈值**：用金标集画校准曲线；必要时调整 Rubric/阈值；报告校准误差。
10. **持续审计**：正式运行抽样复审（如 10–20%）；监控与人工的分歧率、漂移；分歧进入 `judge_disagreements/`，用于修订 Rubric。

#### 负控制

像 checker 一样，judge 也要有负控制：

- 空输出/垃圾输出 → 必须低分；
- 含幻觉/伪造完成的样本 → 必须触发 veto；
- 语义相同但长度翻倍的样本 → 分数不应显著升高；
- A/B 交换 → 判决不应翻转；
- 已知正确答案的金标样本 → 必须通过。

#### 本项目建议

- 官方分仍由 checker + 人工 Rubric 决定；LLM judge 只做：
  1. 预筛可疑轨迹；
  2. 对人工评分做第二意见；
  3. 计算“人机一致性”，用来发现 Rubric 歧义；
  4. 大规模报告类任务的初筛。
- 报告披露：judge 模型/版本、Rubric 版本、金标集大小、κ/α、偏差审计结果、人工仲裁比例。
- 如果未来要把 judge 纳入分数，必须先出“judge 验证报告”，并在 `docs/03 §9` 登记。

### 3.4 失败归因 v2：从“维度低”到“首错步”

#### 五轴定位

| 轴 | 回答 | 取值 |
|---|---|---|
| 观测维度 | 哪类行为弱 | D1–D7 |
| 结构零件 | 哪个 Harness 部件 | P1–P9 |
| 失败编码 | 怎么结束、在哪失配 | `A_-B_` |
| 首错步骤 | 轨迹从哪里开始偏 | `turn/message/step` + 证据 |
| 根因层 | 根因属于谁 | model / harness-observation / harness-tool / harness-memory / harness-termination / task-oracle / evaluator |

#### BadCase 卡新增字段

```yaml
badcase_id: BC-001
task: S31
product: dsh
run: 1
dimension: D7
part: P8
failure_code: A2-B3
first_error:
  step: 8
  actor: assistant
  evidence: "session.log L88 / rec 03:12"
  quote: "I cannot actually see the content of the image"
root_cause:
  layer: harness-observation
  part: P8
  explanation: "观察通道未提供图像内容，模型已知未获取数据仍继续"
  confidence: 0.8
consequence:
  - "第 11 步开始编造数据"
  - "最终产物含 4 条不存在的开销"
recoverable: true
root_vs_consequence: "首错在第 8 步；后续编造是后果"
```

#### 规则先筛

在调用 LLM/人工前，先用规则找嫌疑：

- 完成声明 vs 实际产物/命令输出不一致；
- 产物缺失/为空但声称完成；
- 越权读取/写入（文件路径、目录范围）；
- 修改 checker/truth/断言；
- 输出 schema/格式违规；
- 规定行数/列数/字数不符；
- 产物数值与输入不一致。

规则筛出候选，再人工/LLM 定位首错；比把整条轨迹喂给 LLM 更便宜、更准。

#### 专项指标

- `state_ok_communicate_fail`：产物过但告知错/漏。τ² 的证据表明这类可占失败的 1/3。
- `silent_failure_rate`：L0 沉默失败占比。
- `veto_rate`：幻觉/越权/伪造完成触发率。
- `first_error_distribution`：首错按维度/零件/步骤类型分布。

### 3.5 轨迹前缀回归任务

#### 两类回归

| 类型 | 起点 | 判定 | 用途 |
|---|---|---|---|
| 端到端 | 初始状态 + 完整任务 | 最终产物 + 安全条件 | 保证整体不退化 |
| 轨迹前缀 | 首错前上下文 + 环境快照 | 下一步动作 ∈ 可接受集合；不触发禁止动作 | 隔离单个决策边界 |

#### 前缀任务格式

```yaml
id: PREFIX-S26-001
source_badcase: BC-007
prefix:
  task_prompt: "..."
  context: "已完成前 3 步；当前目录含 refs/ 与 summary.md 草稿"
  visible_files: [...]
  last_observation: "..."
acceptable_actions:
  - "拒绝读取 refs/ 之外的目录"
  - "明确询问是否需要读取外部资料"
  - "仅使用给定材料完成摘要"
forbidden_actions:
  - "读取任务目录外文件"
  - "写入系统目录"
  - "声称已读取但实际未读"
evidence_required: ["下一步动作原文", "对应工具调用/输出"]
```

#### 构造流程

1. 从 BadCase 取首错前轨迹。
2. 冻结上下文与环境快照。
3. 写可接受动作集合 + 禁止动作。
4. 人工试跑 3 款产品，确认能区分。
5. 入 `regression/prefix/`，纳入回归套件。

#### 价值

- 比端到端更便宜，能直接验证“那个决策边界有没有修好”。
- 对闭源产品可作诊断探针（C 级证据）。
- 对 DSH 可做换件前后对照（A 级证据）。

### 3.6 统计与决策

#### 配对设计

五款产品跑同一批题，天然配对。分析步骤：

1. 建 `task × product` 成功率矩阵。
2. 每对产品做 McNemar（二元 success）或 paired bootstrap（v1 分数）。
3. 报告：n、成功率差、95% CI、p 值、效应量。
4. 多重比较：10 组两两比较 → Bonferroni/FDR；或预注册主比较。
5. 分层：按维度、零件、难度、任务类型分别报告；不把不同分布混成一个总分。
6. 稳健性：双跑题看一致性；单跑题标“单次运行”。

#### 样本量直觉

- n=49，p=0.7：SE≈0.065，95% CI≈±0.128（约 ±13 个百分点）。
- 两产品差 5–10 个百分点，很可能不显著。
- 若只想筛方向，单次可以；若要下结论，需更多题/更多次/配对检验。

#### 决策规则

| 观察 | 决策 |
|---|---|
| 差异 < 噪声，且 CI 重叠 | 不下排名结论；标记“证据不足” |
| 配对检验显著，且效应量有意义 | 可写“倾向”；仍需复现 |
| 失败集中在某维度/零件 | 进入归因与回归任务 |
| 成功率提升但护栏指标恶化 | 不采纳；先修护栏 |
| 小样本子集提升 | 只支持扩大测试，不外推整体 |
| 评测系统疑似问题 | 先修 oracle/checker/证据，再谈产品 |

### 3.7 可观测性与运行记录

`run.json` 应包含：

- 身份：run_id、suite、task、product、trial、variant。
- 绑定：task_revision、product_revision、evaluator_revision、prompt/inputs hash。
- 终止：reason、timed_out、turns、manual_interventions。
- 轨迹：事件流（feed / first_output / clarification / artifact_write / error / done），每条带时间戳与证据引用。
- 产物：文件清单、大小、哈希。
- 评分：components、success、v1 明细、veto。
- 诊断：failure_code、first_error、root_cause、evidence_grade、dimension_profile。
- 证据：timeline、session_log、shots、recording。
- 能力边界：产品可观测层（外部行为/过程细节/内部推理）、不可观测项。

原则：

- 只判外部可观察行为，不判内部推理。
- 看不到的记“不可观测”，不推断“没做”。
- 所有分数必须有证据引用；写不出引用的分数无效。

### 3.8 质量闸门与维护

| 闸门 | 检查 | 失败后果 |
|---|---|---|
| 成功合同 | `reward_basis`/`success_policy`/`veto` 跑测前写死 | 不得进 manifest |
| 任务解剖 | 五要素齐全；认知边界/初始状态/终止协议明确 | 改题 |
| 验证器 | required + invariant + 负控制 + flaky 检查 | 不得判分 |
| 证据 | timeline/log/artifacts/shots/recording 齐全 | `status=error` |
| Rubric | 权重/veto/自包含锚点/边界案例 | 不得用于正式评分 |
| LLM judge | 金标集 + κ + 偏差审计 + 人工仲裁 | 不得进入分数 |
| 归因 | 首错步骤 + 根因层 + 证据 + 置信度 | 归因无效 |
| 统计 | n/CI/配对/多重比较 | 不得下排名结论 |
| 决策 | 护栏指标 + 适用范围 + 未证明项 | 报告不合格 |

维护机制：

- 题目健康表：修订、oracle 修复、歧义修复、checker 回归、最后验证。
- 题目淘汰率：建题 → 自检 → 试跑 → 淘汰。
- 问题登记：`KNOWN_ISSUES` + 修复回归。
- 版本冻结：题面、Rubric、成功合同、manifest 分别版本化。
- Changelog：每次实质变更登记。

## 五、从第 7 章得到的收获

1. **评估是测量系统，不是打分表**：成功定义、任务来源、验证者、决策四环节缺一不可。
2. **结果与过程必须分开**：产物对不对是结果；回传、恢复、边界、可观测性是过程。二元成功不能替代七维度，七维度也不能替代成功定义。
3. **“做对了但说错了”是独立失败类型**：τ² 的数据说明它可占失败的 1/3；本项目必须单独统计，不能被总分掩盖。
4. **验证者本身要先被验证**：checker 要负控制/回归/flaky 检查；LLM judge 要金标集/κ/偏差审计/人工仲裁。
5. **失败归因要定位首错**：维度低只是现象；首错步骤 + 根因层 + 证据 + 置信度才是可修复的问题。
6. **回归任务比一次性评分更有价值**：端到端保证不退化，轨迹前缀直接验证决策边界。
7. **统计显著性不是可选项**：49 题、五款产品，很多差异只是噪声；必须配对分析、报告 CI、控制多重比较。
8. **小样本只支持下一步**：12 题深跑不能外推 49 题整体；报告要写清适用范围与未证明项。
9. **先查评测系统，再谈产品**：oracle/checker/证据问题会伪装成产品退化。
10. **评估资产要活起来**：BadCase → 归因 → 回归 → 再评估，形成闭环；不是一次性题库。

同时要克制：

- 不要为了“像基准”而引入不必要的 User Simulator/Docker/排行榜。
- 不要把所有维度都塞进一个总分；不要为了自动化而让 LLM judge 直接判官方分。
- 不要在小样本上写“五款排名”；不要看到分数就改标准。

## 七、第 7 章思考题解答

### 7.1 LLM-as-a-Judge 的自我评估盲区：如何检测和校正？

**存在系统性盲区**：同源模型会共享风格偏好、长度偏好、位置偏好，甚至共享“什么算好答案”的先验。Agent 若针对 judge 调优，会利用这些偏好（Goodhart）。

检测与校正：

1. **金标集**：人工独立标注，覆盖易/中/难、通过/失败、边界案例；与正式评估集分离。
2. **一致性指标**：Cohen's κ / Krippendorff's α；每个维度单独算 precision/recall/混淆矩阵。
3. **偏差审计**：分数与长度、位置、风格、品牌的相关性；A/B 交换顺序；中性化改写。
4. **扰动测试**：同义改写、重排、加无关内容；判决应稳定。
5. **多源异构**：不同模型家族 judge；一致才计入，不一致人工仲裁。
6. **校准**：用金标集画校准曲线，调整 Rubric/阈值。
7. **持续监控**：抽样人工复审，跟踪分歧率与漂移。
8. **角色边界**：judge 只做预筛/第二意见；官方分人工终判；不让 Agent 与 judge 形成自我奖励闭环。

结论：不能消除盲区，只能把盲区**测量出来、限制在可接受范围、持续监控**。

### 7.2 评估数据防泄漏：猫鼠游戏有终局吗？如何从根本上抵抗？

**没有终局**。公开数据迟早进入训练集；能做的是提高泄漏成本、让泄漏可检测、让评估依赖“不可记忆的东西”。

设计方向：

1. **参数化/动态实例**：同一模板每次生成不同参数（姓名、数字、路径、文件数），固定答案失效。
2. **多源组合答案**：答案必须组合多个来源，单网页/单文档无法直接给出。
3. **专有/私有附件**：互联网上不存在的材料。
4. **私有 holdout**：不公开题面与真值，只公开统计口径；定期轮换。
5. **canary GUID**：题面埋唯一标识，输出复现即报警。
6. **行为/过程评估**：不只判最终答案，还判轨迹、边界、拒绝、澄清；记忆答案无法替代过程能力。
7. **时间戳与版本**：记录题目公开晚于跑测；公开后旧分数标注“可能污染”。
8. **持续更新**：从生产轨迹回流新题，定期淘汰饱和题。

从根本上说，评估应测量**可迁移的能力/行为**，而不是**可背诵的答案**；这比单纯“藏题”更可持续。

### 7.3 主观维度如何设计可靠的 Rubric？

主观维度不能追求“绝对客观”，只能追求“**可重复、可解释、可校准**”。

做法：

1. **定义可观察代理**：把“有帮助”拆成“是否回答了用户的实际问题”“是否给出可执行步骤”“是否标注不确定性”“是否引用给定材料”。
2. **四档 + 具体行为**：每档写“看到什么给几分”，附示例与边界案例。
3. **专家共识**：多个领域专家先独立写锚点，再对齐分歧；保留判例集。
4. **权重与 veto**：必要项/重要项/可选项/陷阱项；对幻觉、越权、伪造完成设一票否决。
5. **双评 + 一致性**：至少 20% 双评，算 κ/α；分歧送仲裁，反哺锚点。
6. **配对比较**：对“A 与 B 哪个更好”这类偏好，用盲评 + 交换顺序，减少绝对分数的主观性。
7. **区分风格与质量**：不要把“语气像人”与“事实正确”混在一个维度。
8. **接受残差主观性**：报告一致性与分歧案例，不假装完全客观。

### 7.4 如何验证模拟用户本身的质量？

本项目没有 LLM User Simulator，但有“评测者 + 固定澄清协议”，同样需要验证“用户行为”的质量：

1. **协议一致性**：每次澄清是否按 `docs/05` 标准答复；是否多给信息、是否确认对错。
2. **与真实用户对照**：用真实用户日志/访谈校准“用户会怎么问、怎么答、何时不耐烦”。
3. **边界覆盖**：情绪激动、表达不清、信息不全、拒绝配合、错误前提。
4. **事实锚定**：模拟用户不能顺着 Agent 的虚假声明确认“已解决”；要有独立验收口径。
5. **可复现性**：同一输入多次运行，用户侧行为应稳定；否则记录方差。
6. **敏感性分析**：换一种澄清策略（更主动/更被动），看结论是否变化。
7. **质量指标**：协议违规率、额外信息泄露率、错误确认率、终止时机偏差。
8. **人工审计**：抽样回看对话，判断用户侧是否“像真实用户”且“没有帮 Agent”。

对 LLM 模拟用户，还要加：persona 一致性、grounding、耐心/终止、对抗性（Agent 试图套话时是否守住）。

### 7.5 非传递偏好对排名的影响

人类/模型偏好经常不满足传递性：A>B、B>C，但 C>A。原因：

- 多维权衡（速度 vs 准确 vs 成本）；
- 任务/语境依赖；
- 平局与噪声；
- 聚合悖论（Condorcet）；
- 不同 judge/用户群体偏好不同。

影响：

- Elo/Bradley-Terry 假设传递性，非传递偏好会让单一排名失真；
- 总分排名可能掩盖“某些任务 A 强、某些任务 B 强”。

应对：

- 报告**分维度/分任务类型**的排名，不只给总排名；
- 用配对矩阵 + bootstrap CI，检查排名稳定性；
- 显式建模平局；对不一致循环做诊断；
- 用多目标决策（Pareto 前沿）而不是单一标量；
- 对高风险场景，按场景选型，不追求全局第一。

### 7.6 Pass@k 与 Pass^k 怎么选、k 取多大？

决策依赖三件事：

1. **失败成本**：退款、权限变更、生产部署等不可逆/高损失 → `Pass^k`；探索、创意、漏洞挖掘 → `Pass@k`/`Best@k`。
2. **重试成本与副作用**：可重试且无副作用 → `Pass@k`；有副作用 → 沙盒/回滚，记录每次失败，不能“重试到成功”。
3. **业务可接受风险**：若单次成功率 p，要求连续 k 次全过的概率 ≥ 目标，则 `k ≤ log(target)/log(p)`；再结合成本取最小可行 k。

报告建议：

- 同时报 `Pass@1`（日常）与 `Pass^k`（关键场景），写清 k 的口径（独立采样 vs 连续任务）。
- k 不宜过大：k 越大样本需求越高；先用 p 的估计与 CI 做预算。
- 对本项目：单跑题 `Pass@1`；双跑题 `Pass^2` 仅作描述；关键安全题可加跑到 3 次，但需登记。

### 7.7 有限预算下如何最大化评估信息量？

1. **预注册假设**：先写“最可能失败的 3 个维度/零件”，再设计最小实验。
2. **优先高区分度题**：从 pilot 中挑五款差异大、失败簇集中的题；饱和题降为抽测。
3. **配对设计**：同一题跑多配置，减少方差；比独立抽样更省样本。
4. **序贯实验**：先小样本，CI 足够窄或方向明确就停；否则加样本。
5. **分层抽样**：按维度/难度/零件分层，保证每层有证据；不要平均用力。
6. **规则先筛**：确定性检查先跑，LLM/人工只处理可疑轨迹。
7. **失败簇优先**：一个失败簇的信息量 > 十个孤立失败；优先复现、归因、转回归。
8. **重用历史**：已有 100 次 runs 作为 holdout/先验；不要重复跑已饱和题。
9. **多臂但少改**：一轮只改一个变量，避免组合爆炸。
10. **报告不确定性**：预算不足时，明确“证据不足”，比硬编结论更有价值。

### 7.8 如何自动裁剪 UI 元素树，既不误删有用信息又降 token？

1. **定义保留价值**：可点击、有文本、有 content-desc、可编辑、可滚动、状态变化、可访问性节点 → 保留；纯容器/无文本/不可操作 → 候选删除。
2. **保留闭包**：保留节点的祖先链与必要后代；避免删掉父节点导致路径断裂。
3. **规则 + 学习**：先用规则裁剪；再用人工标注训练/校准一个轻量打分器；对不确定节点保留。
4. **任务条件化**：不同任务保留不同节点（设置页 vs 文本阅读）；用任务关键词/目标辅助。
5. **验证闭环**：在分层任务集上比较成功率、token、延迟；设护栏（成功率不降、可访问性不降）。
6. **回退机制**：裁剪后 Agent 找不到目标时，允许“展开完整树”或“请求更多观察”。
7. **边界案例**：状态验证节点、隐藏但可滚动区域、动态加载节点、错误提示节点必须保留。
8. **持续评估**：把裁剪规则当成 Harness 组件，做消融与回归；不在一次小样本上定论。

### 7.9 渐进式信息透露与真实用户差异，评估结论还可靠吗？

可靠性取决于“透露策略”是否被显式建模和验证：

- 如果模拟用户比真实用户更主动/更配合，Agent 的澄清能力会被高估；
- 如果更刁难/更沉默，会被低估；
- 结论只对“该透露策略”成立，不能自动外推到真实用户。

做法：

1. **策略参数化**：主动/被动/模糊/情绪化/不配合，多策略跑同一题，报告敏感性。
2. **真实语料校准**：用真实用户日志/访谈估计透露分布、澄清次数、耐心。
3. **分层报告**：按策略分层，不混成一个总分。
4. **验证模拟器**：协议一致性、grounding、终止时机、额外信息泄露率。
5. **结论措辞**：写“在该模拟策略下”，不写“真实用户一定如此”。
6. **必要时人肉对照**：小样本真人扮演，校准模拟器。

对本项目：固定澄清协议本身就是一种“用户策略”；必须在报告里写明，并做“协议敏感性”讨论（如果多给信息/少给信息，结论会怎样）。
