# 16 · dsh 三篇文档精读（评测视角）v0.1

> 触发：课题需借鉴 deepseek-ai/deepseek-harness 的公开文档（`docs/testing.zh.md`、`docs/architecture.zh.md`、`docs/capability-seams.md`），但三篇**都不以"评测"命名**，需先判定哪一层属于评测、哪一层只是工程自证，避免把"回归测试"当成"能力评测"照搬。
> 结论：**三篇不是评测方案，是"评测基础设施"的参考实现。** 它们分别回答三个问题——`testing` = 怎么证明 harness 没坏；`architecture` = 用什么单位计量、证据从哪来；`capability-seams` = 换哪个变量做对照实验。其中 6 条判据可直接并入 `docs/03` 复核机制，`turn/step` 定义应作为 `usage.json.turns` 的唯一定义；**三篇均不含** benchmark 任务集、rubric、pass@k、跨产品比较，不可当评测方案抄。

## 一、`testing.zh.md`：一门"如何证明 harness 没坏"的方法学

### 1.1 它到底在回答什么问题

全文没有一句"评测"。它回答的是：**一棵每天都在改的插件树，怎么保证改动没把已有行为弄坏。**

由此得出全文最重要的判断：

| | DSH 的 testing | 本项目的竞品评测 |
|---|---|---|
| 目标函数 | **不变**（改动前后行为一致） | **差异**（不同实现谁更好） |
| 参照物 | 上一版自己 | 同题的其他产品 |
| 失败定义 | 绿灯变红 | 分数低 / 归因不明 |
| 结论形式 | 通过 / 阻断 | 分数 + 证据等级 |

**→ 能借的是"冻结与取证的机制"，不能借的是"判据"。** 这是后面所有取舍的总闸。

### 1.2 七个层级（按"证据强度"排，不是按重要性排）

| # | 层级 | 命令 | 需密钥 | 证据形态 | CI 门禁 | 对我们的用途 |
|---|---|---|---|---|---|---|
| L1 | 单元测试 | `test` | 否 | 断言 | — | 参考：每个注册表都有 HMR-safe 测试 |
| L2 | 覆盖率门禁 | `test:coverage` | 否 | 数字（逐文件 100%） | 门禁级 | **反面教材**：见 §1.3 判据① |
| L3 | 真实 API e2e | `test:e2e` | **是** | 断言 + 真实副作用 | — | 直接对应我们"真跑五款" |
| L4 | 预期输出 | `test:expected` | 否 | 组装产物的预期 | CI 针对构建产物 | 参考：无密钥版的"可回归基线" |
| L5 | 性能基准 | `test:bench` | 否 | 数值预算（耗时/堆/缩放） | **Linux PR gate** | 参考：`elapsed_seconds` 只做描述统计 |
| L6 | 快照 | `test:snapshot` | 否 | **整段 transcript（录制回放）** | — | ★ 最接近我们的"轨迹证据" |
| L7 | Web 浏览器快照 | `test:web` | 否 | **像素 + ARIA 树** | **Linux PR gate** | 参考：UI 类产物的取证方式 |

两条正交的轴，读这张表的关键：

- **轴一「外部世界有多真」**：L1/L2 全假 → L4 组装真但无密钥 → L3 真模型真网络。**只有 L3 能证明"产品能用"**（原文语）。
- **轴二「证据留成什么形态」**：断言 → 数值预算 → transcript → 像素/ARIA。**越往下越像评测，越往上越像回归。**

> 我们目前主要活在 L3（真跑）和"人工 timeline"之间，缺的是 L6 那种"可回放的 transcript 形态"。`docs/13` 提的 manifest/pin 正是在补这一层。

### 1.3 六条判据（原文明确写出，可逐字引用）

#### ① 覆盖率是必要条件，永远不是充分条件

> 原文：「行覆盖率是必要条件，但永远不是充分条件：它证明行被执行过，不证明功能按交付预期工作。」

**落点**：我们的质量关卡不能只写"checker 有覆盖"，必须写"checker 能区分对错"——这正是负控制的正当性来源（S 批 35/35 负控制复核）。

#### ② 无密钥只证明通路；带密钥才证明能用

> 原文：「无密钥测试只能证明底层通路；只有带密钥运行才能证明 agent 能对接真实模型正常工作……价值最高的是**冒烟测试**：启动已交付的 profile、发送一条提示词，并检查外部世界；它们能捕获『单元测试全绿、产品却坏了』这一类 mock 无法发现的问题。」
>
> 附注：「我们是 DeepSeek，不要吝惜真实 API 测试。」

**落点**：文档点名要"检查**外部世界**"，不是检查模型回答。这与我们"checker 只认磁盘产物、不认回答文本"（T00 校准题）完全同构——**双方独立得出了同一条结论**，可作为 `docs/03` 该条的证据等级提升依据。

#### ③ 只 mock 高开销或不确定的边界

> 原文：「只 mock 开销高或不确定的边界（LLM 适配器、网络、时钟）；下游一切保持真实。手写替身只能证明桥接层在搬运字节，不能证明交付的工具行为符合断言。」

**落点**：我们"不 mock 产品本身、只控制任务输入"的选择是符合该判据的；需要补的声明是——**模型是唯一被允许的不确定边界**（对应 `docs/01 §4.4` 模型变量边界声明）。

#### ④ 验证外部世界，而非自我报告 ★

> 原文：「e2e 断言应重新运行命令或从外部重新读取文件；对 agent 自身输出做关键词探测会让**作弊的 agent** 通过。断言未修改的文件逐字节一致。」

**落点**：这是全文对我们最有价值的一句。它把"产物分"的三条硬要求写清楚了：
1. 重新读文件，不读回答；
2. 未涉及的文件必须**逐字节一致**（我们目前只查"有没有改对"，没查"有没有多改"）；
3. 关键词探测是漏洞，不是捷径。

> ⚠️ 第 2 条是当前 `docs/03` 的**实际缺口**：S 批有"静默改动"类考点，但 checker 普遍只做正向断言。

#### ⑤ 测试真实入口路径

> 原文：「『真实入口路径』指已发布的产物：包的 `bin` 所运行的是构建后的 `lib/bin.js`，并由普通 `node` 执行，从而暴露 tsx 会掩盖的失败。」

**落点**：等价于我们的"装完即用"——不看开发态、看交付态。对竞品只能近似为：**全新会话 + 默认配置 + 不做任何预热**。

#### ⑥ 守卫只有在回归能让它失败时才有效（自检）

> 原文：「需要添加显式的 `expect('default' in mod).toBe(false)` 加 `unwrapExports` 往返断言，**并证明它有效：引入回归、观察变红、回退。**」

**落点**：这是"负控制"的教科书表述。建议直接写进 `docs/03 §9` 的复核流程：**任何 checker 上线前，必须构造一个必错产物让它变红。**

### 1.4 "何时需要快照"规则 = 我们的"必须看完整轨迹"

> 原文：「每项非平凡的模型可见、协议可见或人类可见变更，都在同一 PR 中添加或更新无密钥录制会话场景；**包级、e2e、仅 mock 和 PR 理由证据不能取代组装后的 transcript。**」

这句话给了我们一条**证据不可替代链**：

```
单测/包级  <  e2e 断言  <  组装后的完整 transcript
```

**落点**：`docs/01 §4.1` 三层证据链可以借这条排序——"回答文本 + 分数"是 e2e 级证据，**只有完整轨迹才能支撑 Harness 层归因**。这与 `docs/10` 首错归因的要求一致。

### 1.5 关于"跑不稳定"的两句狠话

> 原文①：「被隔离的只有进程：端口、可预测路径、外部命名空间和继承而来的子进程都不隔离。**为每个占用的资源负责到 teardown。**」
>
> 原文②：「**只在单独运行时通过的 spec 存在测试缺陷，而非 runner 不稳定。**」

**落点**：
- ② 是"复跑结果不一致"的正确归因——是设计缺陷，不是运气。**这正是埋雷题要跑 2 次的正当性来源**（`docs/08 §2.2`）。
- ① 提醒我们记录"环境残留"：桌面端无容器隔离时，上一 run 的文件残留就是我们的"未 teardown 资源"。

### 1.6 可跳过（与竞品评测无关的工程细节）

- 「测试解析：仅限源码」（vite-tsconfig-paths / 裸导入解析到 `src`）
- 「测试子进程启动模式」（双模式启动器、`--import tsx`）
- coverage partition 并发、fork 意外退出的 PID 诊断
- Session fixture 的 header/payload envelope 与 `.vN` 代际命名

> 这几段占原文约 1/3，是 pnpm monorepo 的 CI 细节。**读它们对评测无增益，弃读。**

## 二、`architecture.zh.md`：评测的计量单位与证据来源

### 2.1 `turn` / `step` 的严格定义 = 计量单位的唯一口径

> 原文：「一个**步骤**是一次模型请求加上它调用的工具。一个**轮次**包含零个或多个步骤：它在领取首条输入之前打开，并在不再欠下任何工作时关闭。」

**落点**：`docs/08 §8.3` 的 `usage.json.turns` 目前没有定义。建议直接引用这条，并补记 `steps`：

| 字段 | 定义 | 备注 |
|---|---|---|
| `steps` | 模型请求次数（含工具调用轮） | 反映"思考-行动"循环次数 |
| `turns` | 从领取首条输入到"不再欠工作" | 可为 1，且**可为 0 步** |

四个边界案例（判分时必须按此判定，否则跨产品不可比）：

| 场景 | steps | turns | 依据 |
|---|---|---|---|
| 一次请求 + 0 个工具 | 1 | 1 | 常规 |
| 一次请求 + 3 个工具后收工 | **1** | 1 | 工具调用不增加 step |
| 用户连发两条，被同一步骤一并领走 | 1 | 1 | 原文 claim 规则：「下一条输入 + 一条排队消息」 |
| 首次 `pre-step` 被拒绝 / 改写为空 | **0** | **1** | 原文：「关闭不含步骤的持久轮次」 |

> ⚠️ 最后一格最容易被记错：**turn 可以为空**，所以 `turns ≥ steps` 不成立、`steps ≥ turns` 也不成立，两个数必须分开记。

### 2.2 `turn flow` 时序 = 首错归因的坐标轴

原文给出的完整时序（节选主干）：

```
turn/start
  领取输入 → 组装 prompt + tool schemas
  → agent/pre-step ................ 可 reject / 可改写（waterfall）
  step/start
  agent/request → prepareCall ...... 取消则系统/用户消息都不提交
  → 追加 user/message
  → 流式 → llm/stream → agent/assistant-stream
  → assistant/message | assistant/attempt
  → tool/call → tools/pre-execute → tools/execute → tools/post-execute → tool/result
  step/end
  还有欠工作 → 下一步
  → agent/turn-stopping ............ serial，可停轮
turn/end
```

**把 `docs/10` 的失败码挂到节点上**，就得到一张"首错定位表"：

| 时序节点 | 事件类别 | 失败形态 | 归因归属 |
|---|---|---|---|
| `agent/pre-step` | waterfall | 输入被拒绝 / 被改写 | **Harness**（前置校验过严/过松） |
| `agent/request` → `prepareCall` | waterfall | 取消、路由解析失败 | **Harness** |
| `llm/stream` | waterfall | 流中断、超时、限流 | **模型/网络**（非 Harness 责任） |
| `tools/pre-execute` | waterfall | 权限/策略拦截 | **Harness**（审批策略） |
| `tools/execute` | — | 工具执行报错 | **Harness**（工具实现） |
| `tools/post-execute` | waterfall | 结果被改写/截断 | **Harness**（削减器，见 §3.3） |
| `agent/turn-stopping` | serial | 提前收工、谎报完成 | **模型 或 Harness**（需看提示词约束） |

> 这张表是本次精读最可直接落地的东西：`docs/10` 现在是"两轴编码"，加上"节点位"就变成三维——**轴①失败现象 / 轴②责任层 / 轴③时序节点**，首错归因可精确到事件。

### 2.3 三个事件域 = 三种证据的持久性

| 域 | 例子 | 持久？ | 能事后复核？ | 评测用途 |
|---|---|---|---|---|
| **会话事件** | `turn/*` `step/*` `user/message` `assistant/message` `tool/*` | ✅ 追加进日志，`session/event` 广播 | ✅ | **唯一可进证据包的东西** |
| **Agent 事件** | `agent/pre-step` `agent/request` `agent/assistant-stream` | ❌ 进程内实时 | ❌ | 现场观察；必须靠录屏/日志兜底 |
| **能力事件** | `fs/*` `tools/*` `telemetry/*` | 取决于监听者是否落盘 | 部分 | 插桩点；不主动记录就等于没有 |

**落点**：这条解释了为什么我们的证据包必须以 `session.log` + `timeline.md` 为主——**流式 chunk 是瞬态的**，事后只能看到 settlement 后的 `assistant/message`。所以"模型当初是不是犹豫了"这类判断，只能靠 `timeline.md` 人工记录，不能靠日志倒推。

### 2.4 「模型可见即已记录」= 可复核性的理论根基

> 原文：「**模型可见即已记录。** 每个模型请求都必须能从日志重建。新增模型可见输入需要会话事件。」

**落点**：
- 给"用 `session.log` 重建模型所见上下文"提供了合法性——**不是我们的假设，是对方的设计承诺**。
- 反过来可做**评分项**：某产品若做不到"日志重建模型可见请求"，其证据等级应从 A 降 B（`docs/01 §4.2` 可加一条判据）。

### 2.5 两个会咬人的细节

**① `assistant/attempt` vs `assistant/message`**

> 原文：「`assistant/attempt` 保留已到达 settlement 的失败、重试、取消与 stream error attempt，**且不添加模型历史**。」

→ "重试"有独立记录，但不进上下文。**这给了我们区分"产品自己重试"与"人 interven(干预)"的判据**：`attempt` 是产品内部行为，`interventions` 才是人工介入，二者不可混记（`docs/08 §8.3` 目前只记后者）。

**② 硬中断会留下证据缺口**

> 原文：「如果进程在 settlement 前硬中断，则不会留下持久 attempt stream。」

→ 崩溃/强杀场景下，日志天然缺一块。报告遇到这类 run 必须声明"证据不完整"，不能当作"模型没输出"。

### 2.6 「新行为归属位置」表 = 对照实验的挂载点

原文 §新行为的归属位置有 24 行，挑出与评测相关的 8 行：

| 想控制的变量 | 机制 | 评测用途 |
|---|---|---|
| 换模型提供方 | 在 `ctx.llm` 注册适配器 | 模型变量隔离 |
| 换上下文裁剪策略 | `ctx.compaction` / `ctx.toolResultPruner` | 长任务失真控制 |
| 换执行环境 | `ctx.sandbox` + `ctx.sandboxPolicy` | 权限形态对齐 |
| 换进程/终端后端 | `ctx.shell` / `ctx.terminals` | 执行层差异 |
| 限制/放开审批 | `ctx.approval` + `ctx.permissionPresets` | "是否要人点确认"的形态差异 |
| 给单个会话不同能力集 | agent preset + `isolate` realm | 变体对照 |
| 存会话到别的后端 | 实现 `SessionPersistence` | 证据导出格式 |
| 拦截请求/工具/轮次 | 对应 `agent/*` `tools/*` 事件 | 插桩观测 |

> 这张表的价值在于：**它把"harness 的差异"枚举成了可指认的坐标**。我们描述竞品差异时，可以借用这套词（"它的审批是可配 seam 还是硬编码"），比"体验不一样"精确得多。

## 三、`capability-seams.md`：一份可换件清单

### 3.1 先看表头四列，再看 `Role`

表有四列：`ctx key | Role | Owner | Implementations | Direct consumers | Companion plugins | Note`。

`Role` 只有四个取值，**这是全表最关键的字段**：

| Role | 含义 | 可否换实现做对照实验 |
|---|---|---|
| `seam` | 可替换能力（Definition + Provider + Consumer 三角） | ✅ **只有这类可以** |
| `core` | 骨架服务，唯一归属 | ❌ 换了等于重写 |
| `service` | 常驻服务（多为 Remote/集成层） | ❌ |
| `bundle` | 组合包（装配层） | ⚠️ 换 = 换整棵树 |

> 全表 100+ 行，`Role=seam` 约 30 余项。**做对照实验只在这 30 余行里选，其余全部跳过。**

### 3.2 十二个与评测强相关的 seam

| `ctx` 键 | 原文要点 | 评测用途 |
|---|---|---|
| `ctx.llm` | 实现含 `llm-deepseek`、`llm-pi-ai`、**`llm-replay`** | 回放适配器 = 离线可复现评测的开关 |
| `ctx.tokenMeter` | 「isolated per-session replay folds; immutable revisioned measurements」 | 成本维度的取数口径（按会话折叠、带版本） |
| `ctx.sessionPersistence` | 「JSONL 后端把 SessionEvent 词汇表持久化为**每 Session 一个 artifact**」 | 证据包的最小单元形态 |
| `ctx.workspaceChanges` | 「每个 workspace/changes 事件宣告的摘要 + 每个文件的 **turn-start / turn-end 对比**，保留到该 Session 释放」 | ★ 直接对应"每轮改了哪些文件"——我们靠人工 `diff` 的事，它是内建能力 |
| `ctx.tools` | 「pre-policy → monotonic guards → around dispatch → post-policy → final-result observation」 | 五段式插桩点，可精确观测"工具调用被谁改了" |
| `ctx.sandbox` / `ctx.sandboxPolicy` | 「部署默认 mode + workspace root 的**唯一归属**；只有沙箱执行器和 provider 读它」 | 环境控制变量的单点，保证 bash 与 fs 不会围到不同根 |
| `ctx.permissionPresets` | 「`workspace-write` / `danger-full-access` 预设，一次切换同时写两个 knob 事件」 | "要不要人确认"的形态差异可被精确命名 |
| `ctx.agentPresets` | 「按 YAML 声明的 preset 版本挂载，绑定 Agent 到 scoped 贡献」 | 变体对照（同模型、不同能力集） |
| `ctx.subagents` | 实现含 `subagent-acp`、`subagent-codex`、`subagent-claude-code`、`subagent-dsh-sdk` | ★ 能把子任务委派给**别的产品**，是"跨产品组合"的天然实验台 |
| `ctx.sessionQuery` | 「精确读、过滤、**traces**」+ 后端加全文检索/排序/片段 | 轨迹检索与抽样 |
| `ctx.messageFeedback` / `ctx.sessionFeedback` | 「Feedback **stays outside model history**」/ 日志级 feedback/record 事件 | 人评标注入口，且不污染上下文 |
| `ctx.sessionTelemetry` | 「捕获、脱敏、交给唯一后端；**其输出离开进程**」 | 遥测出口；也说明"默认不出进程就收不到" |

**补充三个"上下文削减器"**（都在 seam 里，且都会让"模型看到的 ≠ 工具真实输出"）：

| `ctx` 键 | 机制 | 失真形态 |
|---|---|---|
| `ctx.toolResultPruner` | 超大工具结果 → **可回放的单节点表面替换** | 模型读到的是截断版 |
| `ctx.compaction` | 消费 post-step 压力与请求错误恢复事件；**无面向模型的 compact 工具** | 上下文被摘要替换 |
| `ctx.spillStore` | 超大工具文本落盘，返回**定位符 + 检索提示** | 模型只拿到一个"地址" |

> ★ **这是长任务评测的头号失真源**：产品 A 把 10 万字读进来，产品 B 只拿到一个 spill 定位符，产物必然不同。`docs/09` 长上下文类考点应显式声明这条。

### 3.3 三条读表心得

1. **`ctx.agentLoop` 的 Role 是 `bundle`，不是 `seam`。** 原文注：「这是唯一的具体 loop 插件；扩展包依赖 dsh-agent 的事件与服务，而不是这个包。」→ **loop 本身在 DSH 内换不了**，想对照"不同 loop 策略"只能整体换 bundle。这限定死了"可换件实验"的边界。
2. **`llm-replay` + `tokenMeter` 是一对。** 录制回放 + 回放计量 = 无密钥可复现评测的最小闭环。我们要做"同轨迹复算"时，这就是参照实现。
3. **这张表是脚本生成的**（`scripts/gen-doc-graphs.ts`，带完整性守卫，表头注明 do-not-edit-by-hand）。→ 可信度高于手写文档，可直接引用；反之，手写的 `architecture.zh.md` 里若与表冲突，以表为准。

## 四、缺口：回归 ≠ 评测

| 维度 | DSH `testing` 有 | 竞品评测需要 | 结论 |
|---|---|---|---|
| 任务集 / 数据集 | ❌ | ✅ 题库 + 负控制 | 自建（`docs/02`/`09`） |
| 判据 / rubric | ⚠️ 只有"绿/红" | ✅ 0–3 锚点 + 权重 | 自建（`docs/03`） |
| 重复度量 | ⚠️ 重试只到"稳定" | ✅ Pass@k / Pass^k / Best@k | 借 `docs/14 §1.4` |
| 失败归因 | ❌ 只有事件，无归因方法 | ✅ 首错步定位 | 自建（`docs/10` + §2.2 节点表） |
| 统计显著性 | ❌ | ✅ 配对比较 | 借 `docs/14 §1.10` |
| 跨产品比较 | ❌ **单一产品自证** | ✅ 五款同题 | 不可借 |
| 成本 / 时延 | ⚠️ bench 只测自身性能 | ⚠️ 描述统计 | 沿用 `docs/08 §8.3` 口径 |
| 能力上限 | ❌ 只防倒退 | ✅ 难度分层 | 自建（T/S 两层） |

**唯一近似"能力评测"的东西**：`benchmarks/` 的 `session-open` 性能门禁。它测的是"开一个会话多快"，是产品性能而非 agent 能力。

> 一句话：**DSH 的测试回答"我们有没有退步"，我们的评测回答"谁更强"。前者可以 100% 通过，后者永远有排名。**

## 五、反向使用：把 DSH 的测试盲区变成我们的打点

DSH 在 `testing` 里诚实写下了自己的失败模式。**这些正是评审别人 harness 时最该去戳的地方**——它们不是 DSH 的弱点，是**整个品类的弱点**。

| DSH 自认的盲区 | 原文表述 | 我们的对应检查 | 现状 |
|---|---|---|---|
| 关键词探测可被作弊通过 | 「对 agent 自身输出做关键词探测会让作弊的 agent 通过」 | checker 只读磁盘产物，不读回答 | ✅ T00 已立 |
| 单测全绿、产品坏了 | 「mock 无法发现的问题」 | T00 hello-world 冒烟题 | ✅ |
| 源码解析掩盖构建产物问题 | 「暴露 tsx 会掩盖的失败」 | 「全新会话 + 默认配置 + 不预热」 | ⚠️ 部分 |
| 只在单独运行才通过 | 「存在测试缺陷，而非 runner 不稳定」 | 埋雷题跑 2 次比对一致性 | ✅ 12 题 |
| 覆盖 100% 但功能错 | 「必要条件，永远不是充分条件」 | checker 负控制（必错产物须变红） | ✅ 35/35 |
| 快照记录即真理 | 「record 与 refresh 绝不改写 `workspace.expected/`」 | 双轨成功口径 + 人工 rubric | ⚠️ 讨论稿（`docs/13`） |
| 未涉及文件未校验 | 「断言未修改的文件**逐字节一致**」 | checker 增加"不该改的文件没被改" | ❌ **缺口** |

> 最后一行是本次精读发现的**唯一硬缺口**，建议优先补。
