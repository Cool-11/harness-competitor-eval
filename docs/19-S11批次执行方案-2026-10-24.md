# S11 批次执行方案（v0.1 · 2026-10-24）

> 用途：按本文件执行 **S11 × 5 款 × 2 次 = 10 场** 批次跑测，并附带 1 组并发探针。
> 依据：`docs/03-打分细则-v1.md`（冻结）、`docs/15-S06试点运行卡-v0.1.md`（现场纪律）、`tasks/second_tasks/S11-corrupt-recovery/spec.md`（锚点）。
> 执行人：hjs ｜ 判定人：hjs ｜ 本文件只写操作，不改题面、不改权重。

## 1. 目标与范围

| 项 | 内容 |
|---|---|
| 题 | **S11-corrupt-recovery**（1 道） |
| 测点 | 主 **D3 失败恢复**（P6）／副 **D7 可观测性**（P8） |
| 产品 | codex / dsh / workbuddy / yuanbao / doubao |
| 次数 | 每产品 **2 次**（埋雷型，spec 要求）→ 合计 **10 场** |
| 附加 | 并发探针 1 组（dsh，3 会话），**不计分、不计场次** |

**本轮不做**：S26、S31、S06 重跑、任何新题、任何规则改动。

## 2. 排程（并行，不是串行等待）

| 轮 | 内容 | 墙钟（估） |
|---|---|---|
| R0 | 准备：建 10 个工作目录 + prepare + 核对产品配置 | 10 min |
| R1 | run1 × 5 款**同时开跑** | 投喂 10 min + 生成 5–15 min |
| R1-G | 闸门检查 5 条 + collect + checker | 30 min |
| R2 | run2 × 5 款**同时开跑** | 同 R1 |
| R2-G | 闸门检查 5 条 + collect + checker | 30 min |
| 可选 | dsh 并发探针（3 会话） | 20 min |

单轮内五款并行；**闸门只拦“是否继续下一轮”，不拦同轮其他产品**。

## 3. 准备（R0）

```powershell
# 10 个工作目录，一次建完
foreach ($p in "codex","dsh","workbuddy","yuanbao","doubao") {
  foreach ($r in 1,2) { python scripts/sbatch.py prepare S11-corrupt-recovery $p --run $r }
}
```

产出：`F:\tmp_run\S11-corrupt-recovery\<product>\run<1|2>\work\`，内含 `config.json`（**故意损坏 2 处**）与 `data.csv`；同级生成 `prepare.json`（含 `started_at`、`prompt_sha8`、`inputs_sha8`）。

准备后核对三件事：
1. `prepare.json` 的 `started_at` **早于**你投喂的时间；
2. 工作目录里**只有**这两个文件，没有旧产物；
3. `products/products.json` 中五款的版本/账号已填，`run.json` 会自动带入。

> 产品侧根目录：dsh / codex / workbuddy 直接以 `work` 为 cwd；doubao 用 `F:\runs_tmp\...`；yuanbao 为沙箱 `/data/workspace`，需把两个输入文件上传进去。

## 4. 每场 SOP（四步，缺一不可）

### 第 1 步 · 投喂（发送前必须先截 S1）

1. 新会话，不复用 S06 会话；
2. **只粘贴 `prompt.txt` 全文**，逐字不改；**禁止**加“配置可能坏了”“注意路径”等任何提示（题面已自带）；
3. 产品需要附件时，附**工作目录里的** `config.json` / `data.csv`，不要附仓库 `tasks/.../inputs/` 原件；
4. **S1 必须在发送前拍**，画面包含：产品窗口标题 / 会话名 / 时间 / 已附文件。

### 第 2 步 · 现场（生成期间）

| 截图 | 时点 | 必须可见 |
|---|---|---|
| S1 | 发送前 | 窗口标题、会话、时间、输入 |
| S2 | **首次输出**（单独一帧，不合并） | 读取/修复/筛选的执行过程 |
| S3 | 仅当发生 | 澄清提问、报错、越权请求 |
| S4/S5 | 完成后 | 完成语 + 产物路径 + 文件卡片 |

### 第 3 步 · 导出（跑完 **5 分钟内**）

| 产品 | 做法 |
|---|---|
| dsh | 解压 `%USERPROFILE%\.dsh\sessions\<cwd 转义>\<session-id>\session.v4.jsonl.zstd` → `session.log` |
| codex / workbuddy / doubao / yuanbao | 产品有导出就用；没有则当场写 `session.log` 首行 `未提供原始会话导出（<原因>）`，**不要事后用截图重建** |

同时写：
- `timeline.md`：真实墙钟 + 每步 `L#`/`S#` 引用；
- `recording.txt`：产品外部日志（app log / 终端 stderr / 错误栈）；没有就写“产品未提供外部日志”，并列出你查过的目录。

### 第 4 步 · 归档判分

```powershell
python scripts/sbatch.py collect S11-corrupt-recovery <product> --run <n> `
  --work "F:\tmp_run\S11-corrupt-recovery\<product>\run<n>\work" `
  --interventions 0 --turns <轮次> --elapsed <秒>
```

`collect` 会：快照产物 → 跑 checker → 写 `checker_output.txt`、`score.json`、`run.json`、结果表行。
**elapsed 用秒表实记**，不要依赖缺省推算（缺省只在 prepare 先行时可信）。

## 5. 证据最低要求（每场）

```text
run<n>/
├─ prepare.json / manifest.json / usage.json / score.json / run.json
├─ artifacts/                 产物快照
├─ checker_output.txt
├─ shots/  S1-投喂前.png  S2-首次输出.png  S4-S5-完成.png  (S3 视情况)
├─ shots/README.md            帧说明与缺口
├─ timeline.md                真实时间 + 引用
└─ session.log / recording.txt
```

缺任何一项 → 该场标 `record_quality.missing_evidence`，**不得用推断补齐**。

## 6. 闸门

### 每场（7 条，全过才计入有效）

1. `prepare.started_at` < 投喂时间 < 产物 mtime；
2. 产物落在本场 `run<n>\work`（或产品沙箱对应根），相对路径未被改写；
3. 截图 ≥3 且 S1 为**发送前**帧、含窗口标题/会话名；
4. S2 为独立首帧，非合并；
5. `session.log` 为**本轮**真实导出，或明确 `not_applicable`；
6. `timeline.md` 有真实墙钟与 `L#`/`S#` 引用；
7. `run.json.product_config` 非空。

### 每题（3 条，全过才进下一题）

1. 10 场中 ≥9 场满足上述 7 条；
2. checker 全部跑通（exit 0 或有明确失败码，不得“没跑”）；
3. 至少 4 场能给出可签认的 v1 证据。

## 7. 判分口径

- 产物分：checker 原始分（7.0 制）→ 归一分 = 实得/满分 × 6.0。
- 行为分：**沿用 S06 的 4 格口径**（每题 2 个题面锚点 + D1 回传 + 通用过程）：
  | 格 | S11 对应 | 档 3 条件 |
  |---|---|---|
  | D3-1 | 失败恢复｜检测与报告 | 指出 2 处损坏 + 修复 + **继续完成任务**，产物与报告一致 |
  | D7-1 | 可观测性｜定位具体性 | 逐处定位（行号/字段）并说明修复方式 |
  | D1-1 | 回传一致性 | 主动说清做了什么、产物在哪、有无取舍，且属实 |
  | common-1 | 过程可跟随 | 阶段可见；异常主动上报 |
- **两次跑分别判**，不取平均；报告写“run1/run2 是否一致”，这是埋雷题的核心看点。
- 每格必须能写出 `S#` 或 `L#` 引用，写不出就不签。
- 证据等级：单产品单次仍为 **C**；两轮一致可写“跨轮一致”，不升 A/B。

## 8. 并发探针（可选，20 min，不计分）

**目的**：只回答“同时开多个会话会不会互相污染或降速”。

| 项 | 做法 |
|---|---|
| 对象 | dsh（本地可控，且有 18.99 s 单跑基线） |
| 会话 | A=S06、B=S11、C=S26，各独立 `work` 目录 |
| 启动 | 三个会话启动时间差 < 1 min |
| 记录 | 每会话起止时间、产物路径与 mtime、token、是否互相覆盖 |
| 判定 | ①串味：产物出现他题关键词；②串目录：产物落到别人的 work；③降速：并发单题耗时 vs 基线；④直接拒绝开第二个会话 |

结论只有三档：**可并发不污染 / 可并发有污染 / 不支持并发**。写进 `record_quality` 与报告“未纳入正式评测”一节，**不进 v1、不进产物分**。

## 9. 停止条件

1. 某产品**两次尝试**仍拿不到可复核产物 → 标“未知（形态/权限）”，停止追跑，写进未知账；
2. **≥3 款**无法导出会话 → 全批改为 `not_applicable` 并在报告声明，不再逐款纠缠；
3. 总耗时超 **4 小时** → 只完成 run1（5 场），run2 顺延，报告注明；
4. checker 与 spec 口径冲突 → 停跑，先按 `docs/17 G1` 的方式修口径或 checker，**禁止两边都不动**。

## 10. 交付物

1. 10 个 `run<n>/` 现场（按 §5 结构）；
2. `Log-analyse/S-batch/results.md` 新增 10 行；

4. 阶段报告追加一节：S11 结果 + 并发探针观察 + 未知项；
5. `grade.yaml` × 10（`signoff.by: hjs`）。

## 11. 已知风险

| 风险 | 处置 |
|---|---|
| 五款 GUI 无法指定 cwd | 以产品默认根为准，记录 `product_side_dir`；相对路径正确即不扣分 |
| 某产品把 `config.json` 直接重写而非修复 | 属正常行为，只看产物是否按修复后规则筛对 |
| 产品“自行编造阈值”绕过修复 | checker 会判错；行为分 D7-1 记 0 |
| 上传附件被产品改名 | 记录实际名，不影响判分 |
| 会话导出缺失 | 按 §9 第 2 条处理，不补拍、不重建 |
