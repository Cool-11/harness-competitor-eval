# 22 · 运行身份、完全分账与正式准入规范 v1

> 生效：2026-10-30。目的：补齐“执行与覆盖”短板，让每条结论都能回到唯一运行、冻结题包、有效证据和人工终裁。

## 1. 裁判通道与被测 Codex 隔离

- 当前项目对话是**裁判/项目建设通道**，允许读取 checker、truth、历史结果和评分规则，不得作为 Codex 产品能力现场。
- Codex 正式被测时必须使用：**全新空白对话 + 独立临时工作区 + Memory 使用/生成均关闭 + Skills 关闭**。
- 禁止用 `/fork`、side chat 或本裁判对话继续跑；禁止让被测工作区接触 `checker.py`、`spec.md`、`truth.json`、历史产物和得分。
- `memory_state` 或 `skills_state` 不是 `disabled` 的 Codex 运行，脚本会排除在正式比较之外。
- 新运行默认使用 `C:\tmp_run`；这是对已登记的 DSH/F: 盘沙箱异常 U-10 的环境规避。若显式换根，必须重新做接口预检。

## 2. 每次运行的唯一身份

`scripts/sbatch.py prepare` 生成不可复用的 `run_id`：

```text
hev-<带时区时间>-<题号>-<产品>-r<序号>-<随机8位>
```

`run_key` 只表示“题 × 产品 × run 序号”的语义槽位，不能代替 `run_id`。已有槽位禁止覆盖；重跑必须增加 `--run`，产生新的 `run_id`。

每个 `prepare.json` / `manifest.json` / `run.json` 必须共同保存：

| 类别 | 必填信息 |
|---|---|
| 身份 | `run_id`、`run_key`、`record_type=product_run` |
| 题包 | 单题 `task_revision`、suite revision、prompt/inputs 哈希 |
| 产品 | 产品版本、产品配置 revision、账号 |
| 执行态 | 实际模型、工具、权限、Skills、Memory、接口预检 |
| 时间 | 带时区开始时间、结束时间、elapsed |
| 证据 | 证据路径、证据等级 A/B/C/N |
| 终裁 | pass/fail/unknown/invalid/not_applicable、裁判、时间、准入理由 |

## 3. 六类活动完全分账

六种 `record_type` 不得混算：

1. `product_run`：产品真实运行；只有此类可能进入正式比较。
2. `checker_selftest`：checker 自测。
3. `offline_recompute`：对既有产物离线复算。
4. `checker_regression`：golden/partial/tampered/equiv 回归。
5. `bare_model_probe`：裸模型探针。
6. `interface_precheck`：路径、权限、附件、日志等接口预检。

分账中的 `status=passed/failed` 表示该项活动本身是否成功执行，不代表被测产品得分。例如裸模型探针成功完成记 `passed`，其产物得分仍只写在探针证据中。

除产品运行外，其余五类用 `scripts/eval_ledger.py register` 登记唯一 `record_id`、状态和证据路径。`summary` 只按类型计数，不生成产品排名。

```powershell
python scripts/eval_ledger.py register checker_regression "S11 K4" `
  --status passed --evidence "tests/regression/evidence/S11-K4-after.txt"
python scripts/eval_ledger.py validate
python scripts/eval_ledger.py summary
```

已有或新归档的产品现场用 `python scripts/eval_ledger.py sync-products` 引用登记；该命令幂等，只添加尚未登记的 `run_id`，不改写现场。

## 4. 正式比较的硬门槛

正式比较表只纳入同时满足以下条件的 `product_run`：

- `rules_frozen=yes`；
- `task_valid=yes`；
- `evidence_valid=yes`；
- `uncontaminated=yes`；
- `final_ruling` 为 `pass` 或 `fail`；
- `evidence_grade` 为 A/B/C；
- Codex 额外要求 `memory_state=disabled` 且 `skills_state=disabled`。
- 必须是 schema v2、带单题 revision、产品版本快照，且接口预检为 `passed` 或 `not_applicable`；历史 legacy 运行不得事后补字追认。

先终裁，再生成正式表：

```powershell
python scripts/sbatch.py adjudicate S06 codex --run 2 `
  --evidence-grade C --final-ruling pass `
  --rules-frozen yes --task-valid yes --evidence-valid yes --uncontaminated yes `
  --adjudicator hjs --notes "证据路径见 run2/timeline.md"
python scripts/sbatch.py formal-report
```

`unknown` 不判失败、不判满分、不自动给部分分；原始 checker 分可保留作事实，但 `evaluation.success` 置空，正式表排除。

## 5. 未知项纪律

沿用 `docs/18`：每条未知必须写明**影响、下一步、停止条件和截止**。未达到停止条件就继续取证；达到停止条件后转为“形态不支持”或明确局限，不无限追查。

## 6. checker 修订包

每次修订必须同时保存：

1. 修前代码或可复原的 Git blob/commit；
2. 修后代码；
3. 正例；
4. 近似错误例；
5. 防修过头的反向对照；
6. 独立人工验收人与日期；
7. 修前/修后输出；
8. 历史运行重算影响清单。

缺独立签署时只能写“回归通过、待签”，不得升级为对外结论。

## 7. 结论五段结构

每条阶段性结论统一写：

1. **观察**：本次看到了什么，不夹带原因判断；
2. **证据**：唯一 run_id、文件、行号/截图、哈希；
3. **解释**：当前证据支持的最窄解释；
4. **未排除因素**：尚可能造成同一现象的因素；
5. **可复现实验**：固定变量、唯一改动、重复次数、停止条件。
