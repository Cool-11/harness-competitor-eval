### 3.3 单场现场顺序

1. 新建空白 chat，把 chat 标题、产品版本、账号/配置、实际模型和 reasoning 写入 `timeline.md`。
2. 仅附加 `work` 中两个输入；发送前拍 S1，必须带产品窗口/会话名、时间和附件。
3. 粘贴原始 prompt；不中途干预。首次输出单独拍 S2。
4. 澄清、报错、越权询问或关键恢复行为出现时拍 S3；评测者只按手册允许的固定回复处理。
5. 产品宣告完成后拍 S4/S5：完成语、产物路径/文件卡片和时间可辨。
6. 导出完整 chat/log；记录 turns、人工干预次数、elapsed、termination。
7. 检查 staging `work`，只做复制回收，不先修文件；然后执行 `collect`。

```powershell
python scripts/sbatch.py collect S11 <product> --run 2 `
  --work "<该场 staging work 的绝对路径>" `
  --interventions <整数> --turns <整数> --elapsed <秒> `
  --variant "<必须与 prepare 相同>" --termination product_declared_done
```

每场最终证据至少包含：`prepare.json`、`manifest.json`、`run.json`、`usage.json`、`score.json`、原样 artifacts、`checker_output.txt`、S1/S2/S4/S5（有事件则 S3）、`timeline.md`、完整 session log/导出；录屏可作补充，不能替代缺失的关键截图。截图先放 `F:\for-project-tmp-run\evidence-inbox\S11-corrupt-recovery\<product>\run2\shots\`，再由裁判归档。

截图口径：S1=发送前的空白新 chat、附件、会话/窗口和时间；S2=首次输出；S3=澄清、报错、越权或关键恢复事件，若无事件写 `S3-not-applicable.txt`；S4=产物已经落盘/文件卡片；S5=最终完成语、路径和时间。只有截图仍不够，还必须交付完整产物目录与可获得的 session 导出；否则行为证据或时间证据会降级。

## 5. AutoRubric 优化试验

### 5.1 数据与隔离

运行：

```powershell
python scripts/autorubric_export.py
python -m pytest tests/unit/test_autorubric_export.py -q
```

脚本从已签署的 S06/S11 `grade.yaml` 导出 10 场、40 个行为格；按完整 run 分组，固定为每题 3 场 dev、2 场 holdout，避免同一运行的格子跨集合。公开给 rubric 生成器的 JSONL 去掉产品名、run_id 和人工 rationale；私有 source map 仅供审计。

试验顺序：

1. 用 dev + 两题任务描述生成 rubric v2；生成器不得看到 holdout、产品名、历史总分或人工 rationale。
2. 冻结候选 rubric 和模型配置，再由另一空白 chat 对 holdout 盲评。
3. 与人工 tier 比较：逐格 exact agreement、±1 agreement、加权 κ；同时记录 abstain 和证据不足率。
4. 人工检查所有差异，分类为锚点歧义、证据缺失、标签噪声或模型失误。
5. 只有 holdout 无致命反例且新增锚点能由独立评审者复现，才提议进入下一版；本次不得回写正式分。

当前样本只有两类任务且格子相关，因此只够“发现候选锚点”，不够证明泛化。生产验证至少要扩展到更多任务族，并使用新的、未参与生成的签署样本。

## 6. 未知项与五段结论模板

每条未知必须写：`现象/影响/下一步/停止条件/截止/当前归类`。模板：

```text
U-xx：<现象>
影响：<影响哪些分数或比较，不影响什么>
下一步：<一个可执行取证动作>
停止条件：<得到何种证据即收口；到何时转为“形态不支持”>
截止：<日期或本批次节点>
当前归类：unknown（不自动计分）
```

本周最终结论统一写成：

1. **观察**：只写这次发生了什么；
2. **证据**：run_id、文件/截图、哈希；
3. **解释**：证据支持的最窄判断；
4. **未排除因素**：仍可能造成同一观察的因素；
5. **可复现实验**：固定变量、唯一改动、重复次数和停止条件。
