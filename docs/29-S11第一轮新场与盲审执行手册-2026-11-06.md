# S11 第一轮新场与盲审执行手册（2026-11-06）

> **已被 v3 新场流程替代**：本文的固定 run 编号和强制全程录屏要求不再用于尚未开始的新场。历史准备材料保留；后续按 [评测执行架构 v3](30-评测执行架构-v3-2026-11-06.md) 自动分配新 run，并按 [v3 桌面手工运行卡](31-v3桌面手工运行卡-2026-11-06.md) 取证。不得覆盖已经存在的任何槽位。

## 1. 本轮目标

本轮新增 4 个可正式审计的 S11 产品现场：

1. Codex `run3`
2. WorkBuddy `run3`
3. Doubao `run3`
4. Yuanbao `run3`

DSH 不在本轮重跑，直接使用已有的 `run4`。此前各产品 `run1` 及历史 `run2` 不补造身份，也不覆盖。本轮结束的可检查条件是：四个新场都先 `prepare`、后运行、再 `collect`，每场具有唯一 `run_id`、全程录屏、发送前截图、导出动作证据和原始产物；随后由独立复核人填写 A–E 共 20 个行为格。

建议顺序：Codex → WorkBuddy → Doubao → Yuanbao。先跑最容易核对工作区和设置的产品，可以尽早发现流程问题。

## 2. 运行前只做一次的检查

在每个产品开始前记录当时实际可见的：产品版本、模型/模式、工具、权限、Memory、Skills 和工作区能力。若 `products/products.json` 中的版本已变化，先按实际界面更新登记，再执行 `prepare`；不要沿用旧版本号。

状态字段填写规则：

- 界面明确关闭：`disabled`；
- 产品没有这一能力或控制项：`not_applicable`；
- 无法确认：`unknown`，不要猜；
- Codex 正式运行的 Memory 和 Skills 必须按项目规范关闭，并保留设置截图。

还要确认以下目标槽位都不存在；如果任一槽位已存在，不得覆盖，改用新的 run 序号：

```text
C:\tmp_run\S11-corrupt-recovery\codex\run3
C:\tmp_run\S11-corrupt-recovery\workbuddy\run3
C:\tmp_run\S11-corrupt-recovery\doubao\run3
C:\tmp_run\S11-corrupt-recovery\yuanbao\run3
```

## 3. 证据存放位置

运行工作区统一使用：

```text
C:\tmp_run\S11-corrupt-recovery\<product>\run3\work\
```

界面证据统一使用：

```text
F:\for-project-tmp-run\evidence-inbox\S11-round1-2026-11-06\<product>\run3\
├─ shots\
│  ├─ S0-settings.png
│  ├─ S1-before.png
│  ├─ S2-processing.png          # 能截到时保留
│  ├─ S3-recovery.png            # 能截到错误恢复时保留
│  ├─ S4-complete.png
│  └─ S5-export.png
└─ recording\
   └─ S11-<product>-run3.mp4
```

要求的两个最终文件必须由产品生成并直接导出到该场 `work\`：

- `result.md`
- `error_report.md`

如果产品实际生成或导出了修复后的 `config.json`，原样保留；如果没有，不要人工补写。不要手动修正产品产物、改文件名或整理内容后再收集。

## 4. 每一款产品的标准动作

### 4.1 prepare

在仓库根目录执行。尖括号内容必须替换成界面实际值；不知道的字段写 `unknown`，不要使用推测值。

```powershell
.\.venv\Scripts\python.exe scripts\sbatch.py prepare S11 <product> --run 3 --root "C:\tmp_run" --variant "desktop-default-2026-11-06" --model "<实际模型或模式>" --tools "<逗号分隔的可见工具>" --permissions "<实际权限状态>" --skills-state <disabled|unknown|not_applicable> --memory-state <disabled|unknown|not_applicable> --interface-precheck passed
```

`<product>` 依次为 `codex`、`workbuddy`、`doubao`、`yuanbao`。每次 `prepare` 后立即保存生成的 `run_id`，并核对 `work\` 中只有本次同步的 `config.json`、`data.csv` 等输入。

### 4.2 产品实测

1. 打开全新会话，确认没有历史上下文；Codex 还要确认使用独立工作区且 Memory/Skills 已关闭。
2. 开始连续录屏；录屏必须覆盖发送前状态、发送、处理中、最终回复、文件导出和导出文件落点。
3. 保存 `S1-before.png`：画面应能证明是新会话、题面尚未发送，并显示已选择/上传的两个输入。能显示工作目录的产品还应显示目录。
4. 只发送 `tasks/second_tasks/S11-corrupt-recovery/prompt.txt` 正文和 `inputs/` 中的两个文件。不得发送 `task.md`、`spec.md`、`truth.json`、`checker.py` 或历史结果。
5. 不追加提示、不纠错、不催促。如果产品要求澄清，不回答；保留现场并按 `manual_stop` 收集。
6. 让产品自行完成。保留处理中和恢复动作的截图，但截图不能代替全程录屏。
7. 将产品给出的 `result.md`、`error_report.md` 原样下载/导出到本场 `work\`，同时录下导出动作和落点，保存 `S5-export.png`。
8. 停止录屏。不要重命名或剪辑原始录像。

### 4.3 collect

以下模板每个产品执行一次：

```powershell
$s11Product = "<codex|workbuddy|doubao|yuanbao>"
$s11Work = "C:\tmp_run\S11-corrupt-recovery\$s11Product\run3\work"
$s11Evidence = "F:\for-project-tmp-run\evidence-inbox\S11-round1-2026-11-06\$s11Product\run3"

.\.venv\Scripts\python.exe scripts\sbatch.py collect S11 $s11Product --run 3 --work $s11Work --evidence-mode screen_recording --preflight-shot "$s11Evidence\shots\S1-before.png" --recording "$s11Evidence\recording\S11-$s11Product-run3.mp4" --export-evidence "$s11Evidence\shots\S5-export.png" --interventions 0 --turns 1 --termination product_declared_done
```

若实际为超时、错误或人工停止，要分别改为 `timeout`、`error` 或 `manual_stop`；超时还需加 `--timed-out`。不得为了通过收集而把真实终止原因写成 `product_declared_done`。

## 5. 每场最少需要什么证据

| 证据 | 必须 | 主要支持 |
|---|---:|---|
| `prepare.json` 与唯一 `run_id` | 是 | 运行身份、配置、先 prepare 后运行 |
| `S0-settings.png` | 是 | 版本、模型/模式、Memory、Skills、权限 |
| `S1-before.png` | 是 | 新会话、投喂前状态、输入和工作区 |
| 未剪辑全程录像 | 是 | D3-1、D7-1、common-1、零人工干预、导出链 |
| `S2/S3/S4` 截图 | 尽可能 | 快速定位过程、恢复和最终回复；不能代替录像 |
| `S5-export.png` | 是 | 文件确由产品导出及落点 |
| 原始 `result.md` | 是 | D1-1、D3-1 与产物真实性 |
| 原始 `error_report.md` | 是 | D7-1 与错误恢复说明 |
| 修复后 `config.json` | 条件性 | 仅产品实际生成/导出时保存，不得人工制造 |
| 原生日志/轨迹 | 有则必须 | 补充可见工具动作；没有时明确写“不可见” |

## 6. 四场完成后的盲审交接

1. 私有 subject 对照保存在 `_local/S11-round1-2026-11-06/subject-map.md`，不要交给复核人。
2. 将四个新场的 `run_id`、原始证据路径、关键时间戳和不可见部分写入 `reviews/S11-round1-2026-11-06/reviewer/evidence/` 对应证据卡。
3. 把 `evidence-index.md` 中 A、B、D、E 状态改为“已可复核”。
4. 检查复核包里没有旧分数、`grade.yaml`、`score.json`、checker 输出或建议档位。
5. 交给未参与产品运行、也未修改 S11 checker 的人；对方填写 `review-form.csv` 和 `reviewer-signoff.md`。
6. 收回签署结果后，再由项目方把四格档位登记到各场 grade，并执行正式 adjudicate/汇总。复核人只负责行为判断，不负责改仓库或决定产品排名。

本轮完成后得到的是“五产品各一场可审计观察”的产品实测覆盖，不是稳定性结论。若要讨论重复性，下一轮需要再为四个桌面产品创建新的 `run4`，DSH 则创建新的 `run5`，仍然不得覆盖本轮现场。
