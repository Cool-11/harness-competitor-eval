# 评测执行架构 v3（2026-11-06）

> 本规范只约束 2026-11-06 之后新建的 `hev-v3` 运行。历史现场、分数和旧协议原样保留，不追认、不覆盖。v3 的目标是增加真实执行量，同时把“产品结果”和“Harness 因果”严格分开。

## 1. 结论与最小矩阵

第一阶段只跑 S06、S11 两题，不再用 35 题规模代替正式覆盖：

| 产品表面 | 执行方式 | 第一阶段格数 | 证据模式 | 可支持的结论 |
|---|---|---:|---|---|
| Codex CLI | `scripts/cli_batch.py` 后台批跑 | 2 | `native_trace` | 产品观察；满足 A 轨合同且与 DSH 成对时可进入 Harness 因果 |
| DSH CLI | 同一 runner 后台批跑 | 2 | `native_trace` | 同上 |
| WorkBuddy / 豆包 / 元宝桌面端 | 人工运行 | 6 | `desktop_export` | 当前原生产品配置下的整体结果 |

本项目不照搬 `harness-compare-bench` 的题目、分数或结论。借鉴的是“小型冻结矩阵、可批量执行、先跑后扩”的工程方法；保留本项目自己的场景题、checker、唯一运行身份、证据分层和归因红线。

## 2. 三条比较轨

### A_same_model_cli：Harness 主体轨

只有这条轨可以产生 Harness 因果候选。Codex 和 DSH 必须在同一题、同一 `control_contract_sha256` 下成对正式准入，并满足：

- 唯一变化是 `harness`；
- `model`、`provider`、`reasoning`、`sampling` 完全相同；
- `environment_id`、`permissions` 与外部环境完全相同；网络要么对两边都由外层阻断，要么在 S06/S11 这类离线题中登记为 `not_used_and_trace_verified` 并由原生轨迹复核未使用；
- 两边实际工具集分别冻结并记录，但允许不同：tool schema、工具实现、system prompt、编排、上下文管理和停止策略共同构成被测的 Harness treatment；
- `skills`、`memory` 均为 `disabled`；Codex runner 使用仅含认证文件的临时 `CODEX_HOME`，不继承个人 Skills、Memory、AGENTS、配置或历史会话，结束后立即删除临时认证副本；
- 都使用 CLI、新会话/新 profile、独立工作区与原生完整会话日志；
- 模型配置快照在运行前冻结并保存哈希；
- 两场都经过人工终裁，且为同题、同合同的 Codex/DSH 配对。

脚本会逐项对比合同与实际运行上下文。缺字段、写 `unknown`、只完成一款、合同哈希不同或实际配置不一致，都会得到 `causal_eligible=false`。成功退出、checker 满分或单场 `pass` 都不能绕过该门槛。

A 轨当前把 Codex 放在无自定义配置的隔离 home 中，因此服务方固定为内置 `openai`；`--model` 与 `model_reasoning_effort` 显式进入命令，双方均不得覆盖 provider 默认采样参数。DSH 必须配置到同一 provider，并由原生 session 的 `request/context` 和 `request/header` 反证实际 model、provider、reasoning、sampling 以及工具清单。运行时值与合同不一致时，即使准备表填写一致也不准入。

### B_native_product：原生产品观察轨

用于 WorkBuddy、豆包、元宝，以及使用各自默认模型的 Codex/DSH。它回答“该产品当前配置下做成了什么”，不能回答“差异由 Harness 导致”。不同模型、封闭产品内部 prompt、不可见工具链等变量均保留在产品整体里。

### M_mechanism：机制换件轨

用于 Skills on/off、某一 Harness 组件替换或 A-B-A 反转实验。每次只改变一个预注册变量；Skills 实验只归因到 Skills，组件实验只归因到该组件。M 轨结果不得混入 A 轨的 Harness 整体比较。

## 3. 模型、Skills、Harness 的定责规则

| 观察 | 允许的表述 | 禁止的越界 |
|---|---|---|
| 同题同模型 A 轨成对、外部控制合同一致，执行行为出现可重复差异 | Harness treatment（含 prompt、工具与编排）差异的因果候选；独立重复后再谈稳定性 | 用单场差异宣称稳定优劣，或直接归因到某一个内部组件 |
| 不同模型或产品默认配置比较 | 当前产品配置下观察 | 归因到 Harness |
| 同一 Harness、只切换模型 | 模型配置差异候选 | 归因到 Harness |
| 同模型同 Harness、只切换 Skill，且 A-B-A 反转 | 该 Skill 的机制效应候选 | 归因到整个 Harness 或模型 |
| 多个产品都在同一题以相同方式失败 | 题面、checker、环境或模型的共同原因线索 | 未做对照就判 Harness 共因 |
| 桌面录屏或截图只显示界面动作 | 画面可见行为 | 推断未显示的内部工具调用、cwd 或系统 prompt |

归因过程始终分三层写：`观察事实 → 原因线索 → 受控验证结论`。没有受控反转时停在前两层。

## 4. 证据协议

### CLI：`native_trace`

必须保留冻结解析计划、CLI 版本预检、唯一 `run_id`、实际命令与 cwd、原始 stdout 会话、stderr、超时/退出状态、产物原件与哈希、checker 输出和人工终裁。runner 只执行、收件，不自动终裁。

### 桌面端：`desktop_export`

必须保留发送前截图、完成状态截图、原始会话/日志导出、导出来源与落点证据、产物原件与哈希、checker 输出和人工终裁。录屏改为可选补强证据，不再是 v3 正式准入必需项。

截图证明可见状态，日志导出证明会话内容，产物哈希证明收件内容；三者不能相互替代。桌面导出模式固定进入 `product_result`，不能升级为不可见内部执行行为证据。

## 5. CLI runner 使用

### 5.1 打开 DSH CLI

当前本机安装包含 `desktop`、`headless`、`web` 三个 profile，没有 `tui` profile；直接执行 `dsh tui` 会失败。本项目的 CLI 入口是 `headless`。在 PowerShell 进入项目目录后运行：

```powershell
$env:DEEPSEEK_API_KEY = (Get-Content .secrets\deepseek.key -Raw).Trim()
dsh --profile headless --permission-mode workspace-write --approval-policy never "请在当前目录完成任务"
Remove-Item Env:DEEPSEEK_API_KEY
```

如果需要可连续交互的浏览器界面，可以在同样注入密钥后执行 `dsh web`；它不是本项目的 CLI 正式跑批入口。密钥只进入当前 PowerShell 进程环境，不得粘贴进命令参数、计划 JSON、日志或 Git。退出当前 PowerShell 后环境变量自动失效；同一窗口继续使用时应执行上述 `Remove-Item`。

### 5.2 批量运行

产品默认配置批次使用 [core-cli-v3.example.json](../runner-plans/core-cli-v3.example.json)，它明确属于 B 轨：

```powershell
.\.venv\Scripts\python.exe scripts\cli_batch.py validate runner-plans\core-cli-v3.example.json
.\.venv\Scripts\python.exe scripts\cli_batch.py resolve runner-plans\core-cli-v3.example.json
.\.venv\Scripts\python.exe scripts\cli_batch.py preflight runner-plans\core-cli-v3.example.json
.\.venv\Scripts\python.exe scripts\cli_batch.py run runner-plans\core-cli-v3.example.json
```

同模型 Harness 对照从 [same-model-cli-v3.template.json](../runner-plans/same-model-cli-v3.template.json) 复制到新的计划文件，填满合同、两个 adapter 的同模型配置和配置快照绝对路径。模板中的占位符会被校验器拒绝，防止把未冻结配置误跑成 A 轨。

`run: "auto"` 会在任何 `prepare` 或模型调用之前解析成固定 run 序号，并写入 `_batch-ledger/<batch_id>/resolved-plan.json`。同一 `batch_id` 的源计划之后若变化，runner 拒绝继续。所有 CLI 预检必须一次通过才会创建运行槽。

2026-11-07 实际跑批使用 Codex CLI `0.167.0` 与 DSH CLI `0.2.2-rc.1`。Codex `exec` 的 `--approve-for-me` 已包含 workspace-write 自动审核，不能再与 `--sandbox` 同传；仅传 `--sandbox workspace-write` 会使无人值守工具调用不可用。DSH 默认走官方 `headless` 一次性任务 profile，并要求运行环境存在 `DEEPSEEK_API_KEY`；示例计划用 `required_env` 在 `prepare` 前拒绝缺凭证批次，密钥值不得写入计划或证据。runner 会在任务结束后从 `$DSH_HOME/sessions` 定位 cwd 与本场一致的新 `session.v*.jsonl[.zstd]`，归档它作为原生轨迹。仅有 stdout 最终回复时，该场仍保留为 `unverified` 现场，但拒绝 `native_trace` 和正式准入；修复后必须新开 run，不覆盖旧场。

A 轨的 DSH `configuration_evidence` 应保存运行前 `--dump-config` 得到的最终组合配置（包括 profile、home-level patch 与命令行 overlay），并复核模型服务、推理/采样、权限、网络、Skills/Memory 与遥测设置；工具集作为 Harness treatment 单独记录，不要求和 Codex 相同。配置文件里可能含凭据，入库前只做可复核的密钥脱敏，不删除影响归因的字段。

## 6. 完成和停止条件

- 第一阶段完成条件是 10 个预注册产品格均有唯一身份、原始证据、产物、checker 和人工终裁；`unknown`/`invalid` 原样计入覆盖账，不伪装成有效成功。
- A 轨只有 `formal-results.json` 中 `causal_pairs` 成对且行级 `causal_eligible=true` 才允许进入 Harness 因果分析。
- n=1 只描述一次观察。出现可能改变判断的差异后，才预注册同配置独立重复；禁止看结果后覆盖旧槽。
- S06/S11 跑通前不扩题。录屏不再成为吞吐瓶颈，日志原件与来源证明不得省略。

## 7. 版本影响

v3 替代旧执行卡中“桌面正式场必须全程录屏”的新场要求；旧录屏仍是有效历史证据，不删除。旧执行卡 `docs/27`、`docs/28`、`docs/29` 已从当前方案目录清理，原文仍可从 Git 历史复核；2026-11-06 后的新运行以本文和 `docs/31` 为准。旧运行不会因 v3 放宽取证方式而被追溯升级。
