## 五层最小中台

| 层 | 已有可复用资产 | 下一项可验收的能力与边界 |
|---|---|---|
| 用例层 | `tasks/<批次>/<题号>/` 中 `prompt.txt`、`inputs/` 与 `checker.py`、`spec.md`、`truth.json` 分离；`task_revision`、`evaluator_revision` 绑定版本 | 建立每题机器可读的输入清单、输出契约和观察格索引，由题包生成运行卡；只投喂 prompt 与 inputs。新增题先过正例、近错例、反向对照，不静默修改冻结评分器。 |
| 执行层 | `sbatch prepare/collect`、`cli_batch`、独立 run 槽、环境快照及哈希 | 先补拒收验收，再讨论并发。调度单位为唯一 `run_id`；同一格多次尝试均新建 run 序号，保留原场并显式登记关联。CLI 可受控并发；桌面端仍由人执行。重试仅处理启动/采集基础设施故障，产品失败必须保留为独立观察，不自动重跑到通过。 |
| 判定层 | 每题 checker、`grade.yaml` 行为锚点、`adjudicate` 四项门槛 | 把机械断言结果逐条保存，行为格可累计观察、各自标 evidence/unknown，最后人工签认；`score.json` 的产物分与最终 pass/fail 分开。失败后的复测先登记新身份和停止条件，不能覆盖旧分。 |
| 报告层 | `formal-report`、`coverage_report`、逐场 `run.json`/manifest | 从同一批 run 生成 pass/fail/invalid/pending/unknown、正式准入、证据模式、排除原因与原场→替代场映射。映射须有明确的 `replaces_run_id` 或批次计划证据；当前只有相同题/产品的时间顺序，不能自动宣称后场替代前场。失败归因分为“观察事实、候选线索、受控验证结论”，空 `failure_code` 不强行补原因。 |
| 服务层 | CLI、`pytest` 与运行账校验命令 | 先在 CI 做题包/判卷回归、账表一致性和报告构建；不在公共 CI 调用付费模型或接触桌面账号。通知只推送状态变化、缺证据和人工签认待办。用例管理入口先用仓库索引与运行卡，不为两题另造 Web 服务。 |

## 实施顺序与检查

1. **P0 计数与终裁**：保留 11 月 7 日历史周报，当前报告按同一截止时点读取 `run.json`；检查 27 条记录各自的终裁状态、11 条准入以及十格覆盖。逐格审核应引用 `grade.yaml` 的证据与签认；独立评审缺失不能被脚本补造。
2. **P1 输入与归档拒收**：现有测试覆盖错目录和重复 collect；本次新增跨题输入复制时的 prepare 哈希拒收反例。`collect` 对 v3 题包版本漂移已有拒收。S11 的 `config.json` 本来要被修复，不能在 collect 要求所有工作区输入哈希保持原值。桌面端实际投喂文件是否与准备副本一致仍须依据发送前截图、会话导出和来源证据人工核对；仅凭 prepare 哈希无法证明人没有选错附件。
3. **P1 DSH S11 复测**：先写预注册卡，固定题面、输入、模型、权限、环境、产物契约与唯一改动，并写明无效场、反转和停止条件。分别记录业务筛选是否正确、两份 Markdown 是否交付；不把 ACL 错误线索直接当因果解释。
4. **之后再扩平台能力**：仅在上述验收通过且出现重复工作时，实现输入/断言清单、批次调度、失败分类展示和 CI 接口。每增加一层，都以现有运行身份和证据链作为验收对象。

本页是架构与执行顺序，不产生新的产品运行、人工终裁或因果证据。
