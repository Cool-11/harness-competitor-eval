# Harness 竞品评测：项目拆解、低分原因与执行优先级

> 2026-11-03 本地审阅稿。依据本仓库当前工作树、导师的四份 Week 3 Report issue 和评分截图。仓库有未提交改动；下文的“当前”指本地工作树，不等同于 GitHub 已发布版本。此文是项目分析，不修改正式评分规则、历史记录或产品结论。

## 1. 先把项目定义清楚

**要回答的问题**：五款 Agent 产品执行同一文件任务时，产物、过程、工作区边界和错误恢复分别怎样表现？观察到失败后，能否用原生轨迹、对照运行和排除题目/判卷错误，判断失败发生在哪个执行环节？

**实际价值**有三层：①给用户选择产品提供限定场景下的可复核观察；②给产品开发者指出可复现的执行层缺陷；③给研究者提供“题包—运行身份—原生证据—判卷—人工终裁—归因”的评测流程。现阶段最成熟的是第三层；第一、二层的正式证据仍少，不能把方法建设写成产品能力结论。

一条完整的价值链是：

`问题/假设 → 冻结题与判定条件 → 运行前登记 → 独立产品运行 → 原生证据与产物 → checker + 行为复核 → 准入终裁 → 跨场/对照分析 → 可被推翻的结论`。

对应仓库：`docs/01,03,09,10` 定义问题和尺子；`tasks/` 存题包；`scripts/sbatch.py` 做 prepare/collect/adjudicate/formal-report；`Log-analyse/` 存现场和账；`tests/` 守护判卷；`experiments/autorubric/` 是发现性实验。缺口集中在链条后半段：正式产品运行的广度、重复性、行为独立复核和机制对照。

## 3. 85 分究竟说明什么

截图为执行与覆盖 **17/25**、判卷与用例 **19/20**、证据可复核 **23/25**、归因分析 **17/20**、周报质量 **9/10**，合计 **85/100**。85 分不是项目整体做得差；最明显的相对短板是“执行与覆盖”，比同组 94/92/87 分项目对应项的 23/22/21 分低 6/5/4 分。

导师 [本项目 issue #1](https://github.com/Cool-11/harness-competitor-eval/issues/1) 的直接扣分逻辑：S11 run2 五场没有运行前 `prepare.json`，一些产品缺原生过程证据，DSH 真实 cwd 指向旧 S06；五场均无法正式准入，行为格未独立终裁；AutoRubric 仅两题族、holdout 未盲评；K4 外部独立性仍有限。其认可的是诚实保留 unknown、发现污染和修复判卷错误，并非要求把缺证据的旧场补写成正式样本。

根因可归纳为四个串联瓶颈：

1. **建设工作压过真实实验**：35 题、复杂评分和多份规范先建成，深跑 12×5 的预定矩阵尚未执行。设计完备不等于产品覆盖。
2. **运行身份在发送前未闭环**：事后截图哈希可以索引收件，不能证明运行前工作区、题包和输入已绑定。DSH 错 cwd 是实际反例。
3. **产物分与行为分断链**：checker 只能验可见文件；“是否就地修复”“是否越界读”“错误如何恢复”依赖原生轨迹或可信现场。7/7 不能自动变为正式 pass。
4. **结论问题过多、资源分散**：五款比较、DSH 换件、35 题覆盖、AutoRubric 同时推进，单条结论缺足够重复和独立审查。

## 5. 保留、优化、暂停与删除

| 决策 | 对象 | 为什么 |
|---|---|---|
| 保留 | 题包唯一真源、输入指纹、运行前 prepare、原生轨迹、checker 回归、unknown 与 invalid、人工终裁 | 直接保证结论可追溯；DSH 错目录证明这些不是形式主义 |
| 优化 | 准入状态一处生成并同步正式表、ledger、周报；每条行为分链接证据时点；公开派生件附私档核验收据 | 减少“正式 pass / 台账 unknown”等冲突，缩短评审路径 |
| 优化 | S11 新场的工作区选择预检、实际 cwd 核验、输入全哈希、产物哈希、修前/修后配置 | 消除 run2/run3 的实际失败模式 |
| 暂停 | 新增 S36 以后题目、全 35 题五款铺开、无反例驱动的长篇框架文档 | 当前瓶颈在运行和终裁，不在题数 |
| 暂停或降级 | P8=可换遥测、P7=可关闭停止钩子的 A 级归因宣称 | 已登记的架构证据表明原设想不成立；保留题目观察价值，撤销不成立的换件假设 |
| 从正式结果移出，保留原件 | 旧 S11 run2、污染 run3、legacy S06/S11 | 不能事后补造 run_id；原始事实仍有探索价值 |
| 从当前工作目标移出 | 对所有产品输出一个总排名 | 模型、配置、产品形态与单次方差未受控；现阶段只能给条件内观察与分轨结果 |

“删除”应是删掉**承诺和无效推断**，不删除历史原始证据或篡改旧分。README 仍停在 10 月 25 日状态，`tests/KNOWN_ISSUES.md` 的 K4 日期与周报 K4 时间线不一致；应修正文档索引与时间线，而非删去可审计历史。

## 6. 自动化应围绕已发生的错误

**优先做**：`prepare` 后自动输出发送前核对卡；`collect` 校验 run_id、题包/输入哈希、可得的真实 cwd、产物来源及必需证据，缺项直接标 `unknown/invalid` 原因；从唯一 JSON 账生成正式表、周报数字和排除清单；检测“同一个 run 在 formal 与 ledger 状态冲突”；checker 修订自动跑正例、近错例、反向对照及历史重算差异。

**不应自动判定**：产品是否实际读了某文件、是否真的就地修复、unknown 该给几分、是否归因 Harness。这些可由脚本整理证据，但仍需要原生轨迹和独立人工判断。自动化目标是减少漏采与抄表错误，不是制造不存在的证据。

当前全套 `pytest` 在本地 `.venv` 下有 1 个失败：`tests/unit/test_autorubric_export.py` 预期 10 个 signed run，实际导出 11 个。新增 DSH run4 被动态纳入，说明实验样本冻结没有固定到源 run_id；在修复前不可重导出并宣称原 24/16 拆分保持不变。其他用例运行通过或跳过。系统 Python 没有 pytest，测试使用项目 `.venv`。

## 7. 下一个最小闭环：按交付物验收

**A. 先锁住现有结论（半天级）**

- 对 S11 run2 五场逐格归档“可直接证明 / 缺证据 / 污染 / 产品形态拿不到”，明确停止条件；不追认正式样本。
- 更新本地运行总账快照，使 formal、ledger、周报使用同一截止时间；标出 run4 是 11 月 1 日新增，不回填到 10 月 31 日周报。
- AutoRubric 明确固定原 10 个 run_id；修复测试对新增 signed run 的脆弱假设，再冻结候选、开展 16 格盲评。若结果差于 v1 或有致命误判，停止晋级。

**B. 再拿一组真正可比较的观察（本周核心）**

- 预注册一个窄问题：在 S11 已冻结的输入和规则下，五款各一场新制式运行，分别能否完成“发现损坏→就地修复→交付两份文件→如实回传”？每款只报告该配置下 n=1 的观察。
- DSH run4 可作为这组的已完成样本，但先核查其题包 revision 与其他新场将用的版本一致；不一致则分批，不拼表。另四款新场先 `prepare`，确认产品设置和真实工作区，再发送；不可控制的设置显式写 unknown。
- 每场完成后立即收原生/可得过程、checker、逐格行为证据与独立复核签署。终裁可以是 pass、fail、unknown 或 invalid；**有效失败也算有效执行**，不为提高成功率而排除。
- 交付一张 5 行表：运行 ID、题包/配置版本、产物分、行为格、准入与排除原因、证据链接、结论界限。若产品无法导出过程，只报告可见层，不硬凑正式格。

**C. 有了运行样本再挑机制题（下一阶段）**

- 从 S31（静默异常）或 S13（矛盾）选一个已修过 checker 且可能推翻现有理解的题，先写成功/失败/反例条件；只跑能回答该问题的最小样本。若要说 Harness 因果，优先选择架构上确实可单变量改变的 DSH seam，并设基线/干预/恢复对照。没有可行单变量就只写关联观察。

**完成的判据**：评审者仅凭 5 行索引可找到原题版本、运行前记录、现场、评分依据和终裁；每个 unknown 有原因和停止条件；报告只给数据支持的结论。这个闭环比把 35 题全跑一遍更能修复当前 17/25 的扣分点。

## 8. 最短汇报口径

“我的课题是构建可复核的 Agent 执行层竞品评测。题库和判卷已较成熟，当前短板是正式运行覆盖：S11 run2 五场因运行前身份和部分过程证据缺失，不能进入正式比较；11 月 1 日已有 DSH 单场新制式正式试点。下一步先固定账表与候选 rubric 样本，再按同一冻结任务为其他产品建立新场，逐场完成证据、行为复核和准入终裁，最后只对可反驳的问题做机制对照。”
