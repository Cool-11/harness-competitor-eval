## 一、文件命名

```
周报<两位序号>-<YYYY-MM-DD>.md
```

- 序号从 `01` 起，两位定宽
- 日期用该周最后一个工作日
- **只留 Markdown 留档**；原始 PDF/邮件附件不入库（`docs/week-conclusion/` 已清理）

## 三、每节怎么写

| 节 | 内容要求 | 写法 |
|---|---|---|
| **〇、本周运行账** | 新增独立运行数 / 有效数 / 失败数 / 未知数 + 现场链接 | 只写**本周新增**，不累计；未知要分类（未跑 / 证据不足 / 形态不支持 / 口径未裁），不判 0 |
| **一、本周项目进展** | 3–5 条，覆盖"方向变化 + 实际产出" | 先说**判断/转折**，再说**做了什么**；能被仓库里的文件印证 |
| **二、本周难点突破** | 2–3 条，每条一个"坎" | 格式：`坎X`：<卡在哪> → <怎么想通> → <结果> |
| **三、下周项目计划** | **最多 3 项**，每项带交付物、规模、完成条件 | 用动词开头；不写"继续推进"；完成条件要能被第三方判定 |

## 四、写作要点

1. **进展要能指回证据**：涉及文档/题库/跑测的，尽量能对应到 `docs/`、`tasks/`、`Log-analyse/` 的具体文件。
2. **难点写"想通的过程"**，不只写"已完成"——评审看的是判断力。
3. **数字优先**：运行数、有效数、失败数、未知数，比形容词有信息量；**题量不计分**，只作背景。
4. **不夸大**：未验证的写"待验证"，未完成的写"进行中"；未知项必须带下一步与停止追查条件。
5. **口径一致**：产品名用固定 slug（`codex` / `dsh` / `workbuddy` / `yuanbao` / `doubao`），题号用 `T` / `S` 前缀。
