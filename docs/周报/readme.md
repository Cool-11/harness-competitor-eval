# docs/周报 · 写作参考

> 用途：本目录存放每周邮件周报的仓库留档。本文件是**写法参考**，不是周报本身。
> 参考样本：[周报01-2026-10-17.md](./周报01-2026-10-17.md)

---

## 一、文件命名

```
周报<两位序号>-<YYYY-MM-DD>.md
```

- 序号从 `01` 起，两位定宽
- 日期用该周最后一个工作日
- **只留 Markdown 留档**；原始 PDF/邮件附件不入库（`docs/week-conclusion/` 已清理）

## 二、固定结构

```markdown
# 周报 NN（YYYY-MM-DD）

> **周次**：WNN ｜ **日期**：YYYY-MM-DD ｜ **汇报人**：<GitHub ID>
> **仓库**：<repo URL>
> **说明**：本文为邮件周报的仓库留档，正文与已发送版本一致。

---

## 一、本周项目进展

## 二、本周难点突破

## 三、下周项目计划
```

## 三、每节怎么写

| 节 | 内容要求 | 写法 |
|---|---|---|
| **一、本周项目进展** | 3–5 条，覆盖"方向变化 + 实际产出" | 先说**判断/转折**，再说**做了什么**；能被仓库里的文件印证 |
| **二、本周难点突破** | 2–3 条，每条一个"坎" | 格式：`坎X`：<卡在哪> → <怎么想通> → <结果> |
| **三、下周项目计划** | 3–5 条，可执行 | 用动词开头（"补齐…""批量跑…""产出…"），不写"继续推进"这类空话 |

## 四、写作要点

1. **进展要能指回证据**：涉及文档/题库/跑测的，尽量能对应到 `docs/`、`tasks/`、`Log-analyse/` 的具体文件。
2. **难点写"想通的过程"**，不只写"已完成"——评审看的是判断力。
3. **数字优先**：题量、运行次数、维度数、天数，比形容词有信息量。
4. **不夸大**：未验证的写"待验证"，未完成的写"进行中"。
5. **口径一致**：产品名用固定 slug（`codex` / `dsh` / `workbuddy` / `yuanbao` / `doubao`），题号用 `T` / `S` 前缀。
