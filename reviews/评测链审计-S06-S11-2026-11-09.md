## 发现 1：归档文件的字节哈希在当前工作树不匹配

- S06 run4 的 `artifacts/输出/汇总/月报_v1.md`：manifest `c1bee6a3…`，当前工作树 `30204cda…`。
- S11 run6 的 `artifacts/filtered.csv`：manifest `349fa309…`，当前工作树 `7f01d55e…`。
- 两文件在 Git 索引中为 LF，工作树为 CRLF；将当前字节的 CRLF 还原为 LF 后，SHA-256 均与 manifest **完全一致**，而 `git show HEAD:<路径>` 的原始 blob SHA-256 也与 manifest 完全一致。因此差异可由 Git 检出时的换行转换解释；未发现内容层面的不同。
- 影响：当前工作树的这两份文件不能直接通过“归档原件 SHA-256 = manifest”校验。审计时应优先从 Git blob 或原始收件源取得原字节，并记录取得方式；后续可为审计产物设置稳定的 Git EOL 规则，但不得改写旧 manifest 或冒充旧场原件。

## 发现 2：S06 checker 对“不得增补”的校验不足

`spec.md` 要求“6 条事项齐全（无遗漏/增补）”，而当前 checker 仅统计六个关键词是否出现。只读临时试验：将 golden 月报追加“额外事实：项目已正式上线。”，得分仍为 7.0/7；golden 原件也是 7.0/7。这证明 checker 不能阻止该类增补，**不证明任何历史运行实际发生了增补**。

这属于冻结规则与机械判分实现之间的缺口。若修订 checker，应按仓库规则另建版本、保留正例／近错例／反向对照和修前修后输出，评估历史重算影响并独立签署；本次未修改冻结题包或既有分数。人工语义复核仍应检查超出输入的断言。
