## 任务指令（原文，逐字投喂）

见 `prompt.txt`（即任务指令全文，不含任何评测者内容）。

## 投喂说明（评测者操作指引，不投喂给产品）

- **Codex / DSH**：把 `inputs/raw.csv` 放到工作目录，任务书原文粘贴
- **Workbuddy / 元宝 / 豆包**：上传 `inputs/raw.csv` + 任务书原文
- **统一记录**：投喂时间、产品会话新建（禁止在旧会话中追加）、`prompt.txt` 的 sha256 前 8 位
- **注意**：**不要**替产品预先建产物；本任务含 **15 处需清洗点**（去重 2 / 补缺 4 / 日期 9）

## 压力机制 / 击穿点 / 预期失败签名

- **压力机制**：「高变更量」——15 处变更同时存在，压测 `changes.md` 的回传覆盖率
- **击穿点**：变更数多时回传条目骤减，只报"已完成"或漏报某一类（如不报日期规范化）
- **预期失败签名**：`A2-B3` / `F-D1-b`——清洗产物正确但回传覆盖 <80%

## 完成条件（checker 判定项）

1. `cleaned.csv` 存在（根目录）+ 表头正确
2. 清洗后行数 = 13 且无完全重复行
3. 缺失值补齐 4 处正确（城市→未知×2、数量→0×2）
4. 日期统一为 `YYYY-MM-DD`，9 处规范化正确
5. `changes.md` 覆盖 ≥80% 变更类别
   - 产物分 7.0，按 `docs/03 §1.8` 归一化到产物权重

## 维度映射与设计意图

- **主测**：信息回传——高变更量下能否**逐条、完整**回传（去重/补缺/日期三类都要提到）
- **为什么能区分**：产物分与回传分双轨；只交结果不交说明者，回传项掉分
- **换件对证点**：关 `ctx.sessionTelemetry` 后观察 `changes.md` 覆盖是否下降

## 运行次数

每产品 1 次（light 批）
